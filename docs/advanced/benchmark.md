# 访问性能实测报告

> 这份文件里的**每一个数字都是跑出来的**，不是估算。采集脚本在仓库里
> （`scripts/benchmark/measure.sh` + `scripts/benchmark/loadtest.cjs`），复现命令在第 0 节。
> 如果你的机器上跑出来的数字不一样，先比对第 0 节的环境差异 —— 尤其是"客户端与服务端是否同机"。

## 0. 环境与采集协议（先读这一节，否则数字会被误读）

| 项 | 值 |
|---|---|
| 被测对象 | **生产镜像**（`scripts/build-image-local.sh` 构建的 all-in-one：caddy + Nest server + Next 前台 + waline），podman rootless 起的一套真栈 |
| 运行时 | Node **v24.21.0** / Alpine 3.24、express 4.22.3、@nestjs/core 10.4.22、mongoose 8.24.4、sharp 0.35.4、Next 14.2.35 |
| 压测机 | 同一台机器：Linux x86_64、**6 核**、31,854 MB 内存、fd 软限制 1,048,576、`somaxconn` 4,096 |
| 数据规模 | **53 篇公开文章**（库里 59 篇）、7 个标签、总字数 41,508、每页 5 篇、皮肤 apple；静态文件 **93 条**（图床原图取样 41.8 KB，最大的一张 1.08 MB；缩略图 6.7 KB）；visits 8,747 行、viewers 796 行 |
| 数据来源 | 从一份 66 MB 的生产整站备份恢复（`./vanblog.sh reset`）—— **不是空库**（空库测出来的数字没有意义：没有文章就没有 ISR 页面、没有图片就没有静态流量） |
| 链路 | 客户端 → `127.0.0.1:18080`（caddy，含 `encode` 压缩与安全响应头）→ 反代到 server / 前台；静态图片由 caddy **直接发**（不经 Node） |

⚠️ **三条必须知道的保守性**

1. **客户端与服务端同机**，抢同一批 CPU ⇒ 绝对数字**偏低**，只适合"同一台机器上的前后对比"，
   不能当成"公网能扛多少"。
2. 走 **loopback**：没有真实网卡与排队丢包，也**没有 TLS 握手**（生产是 HTTPS + HTTP/2、HTTP/3）。
   TLS 与拥塞控制会让真实公网延迟高于这里的数字。
3. 页面都是 **ISR 缓存命中**（压测前已预热）。冷启动的首次渲染贵得多 —— 那是另一件事，
   见 `docs/advanced/performance.md` 里关于 `revalidate` 的取舍。

⚠️ **采集时把限流抬掉了**（`VANBLOG_RATE_LIMIT_PER_MIN=100000000`、`VANBLOG_STATIC_LIMIT_PER_MIN=1000000000`）。
不抬的话测到的是"限流器多快返回 429"，而不是栈的容量：默认配置下同一 IP 每分钟 600 次请求就会被拦，
一轮 3,000 请求的压测里会出现 **1,018～1,653 个 429**（这个数字本身也是事实，见第 7 节）。
**这是本轮实际踩过的坑，写下来避免下次再踩。**

复现命令：

```bash
# 1) 构建镜像并起一套干净栈（数据目录用新的，避免污染现有环境）
scripts/build-image-local.sh --build-only
ENGINE=podman IMAGE=localhost/vanblog:local-test RUN_DIR=$PWD/vanblog_dev/bench \
  EXTRA_ENV="VANBLOG_RATE_LIMIT_PER_MIN=100000000,VANBLOG_STATIC_LIMIT_PER_MIN=1000000000" \
  vanblog_dev/run-image-stack.sh --stack-only        # 本机脚本；生产用 docker compose

# 2) 灌入真实数据
VANBLOG_API_BASE=http://127.0.0.1:18080 ./vanblog.sh reset 0 <你的 vanblog-full-*.tar.zst>

# 3) 采集（本报告用的就是这一条）
scripts/benchmark/measure.sh --base http://127.0.0.1:18080 \
  --engine podman --container vb-app \
  --latency-n 20 --sweep-c 50,200,500,1000 --sweep-n 3000 --static-n 800 --c10k 10000
```

- **文章页 78,830 B / gzip 23,729 B，8 ms** —— 一篇 9,610 B 正文的文章，含代码高亮与目录。

  文本该压缩"的依据。

## 2. 页面重量（HTML 与 `__NEXT_DATA__`）

| 页面 | HTTP | HTML 原始 | HTML gzip | __NEXT_DATA__ 原始 | 占比 |
|---|---|---|---|---|---|
| `/` | 200 | 93359B | 22961B | 11548B | 12% |
| `/post/qdii-ji-jin-xian-gou-yu-na-zhi-feng-wei-ji-jin-fen-xi` | 200 | 78830B | 23729B | 12804B | 16% |
| `/timeline` | 200 | 114751B | 24976B | 28934B | 25% |
| `/link` | 200 | 38168B | 13537B | 7971B | 20% |
| `/tag` | 200 | 37345B | 13376B | 7986B | 21% |
| `/page/2` | 200 | 93127B | 21770B | 11269B | 12% |

`__NEXT_DATA__` 是 Next 塞进 HTML 的那份 JSON（hydration 用）：**它随 HTML 一起下载、还要被浏览器再解析一遍**，
所以占比是真实成本。首页从改造前的 **31.8%（gzip 后 54.8%）**降到现在的 **12%**，
原因是列表页不再把文章全文塞进去（AGENTS §7.42、§7.45）。
`/timeline` 仍有 25% —— 那是年份归档本身的数据量（以前更高，因为它把文章数组塞了两份，§7.45 已修）。

## 5. C10K（一万条连接同时挂住，再一起发请求）

- **目标 `/static/img/cc1db5c34b04e07c71a7549fac46c37e.image.webp`：**
  - 目标连接数     : 10000
  - 成功建立       : 10000（用时 1.8s）
  - 连接上发请求   : 200=10000 失败=0（用时 1.4s）
- **目标 `/api/public/meta`：**
  - 目标连接数     : 10000
  - 成功建立       : 10000（用时 1.1s）
  - 连接上发请求   : 200=5872 失败=4128（用时 10.7s）

结论要**分两层**说，混在一起就会得出错误的乐观或悲观：

- **连接层（caddy）从来不是瓶颈**：一万条连接 1.1–1.8 秒全部建立，0 拒绝。
- **静态内容：一万条连接同时取图 = 10,000/10,000 全部 200，1.4 秒，0 失败** —— 这就是 C10K，已经做到。
- **动态内容（要反代到 Node）：一万条同时请求 `/api/public/meta`，10.7 秒内完成 5,872 个**，
  其余没能在客户端 30 秒超时前排到。**天花板是单进程 Node 应用层**，不是网络层。
  这个数字在持续上涨（同一台机器、同一份数据：§7.44 时是 **1,600**，meta 并行化 + 5 秒缓存后 **3,672**，
  现在 **5,872**），但要再上一个量级只能靠多进程（第 10 节）。

## 7. 默认配置下的行为（不抬限流）—— 这一节是给运维看的

同一套压测在**默认限流**下：混合流量 3,000 个请求里，并发 50 时 **1,018 个 429**、并发 500 时 **1,653 个 429**；
一万条连接同时打 `/api/public/meta` 只成功 **600 个** —— 正好等于默认的
`VANBLOG_RATE_LIMIT_PER_MIN=600`（每 IP 每分钟）。

这不是故障，是**设计如此**（反扫描兜底），但有两件事必须知道：

1. 静态资源走**独立且宽 10 倍**的桶（`VANBLOG_STATIC_LIMIT_PER_MIN`，默认 = 全局 ×10）。
   以前图片和 API 抢同一个桶：一篇带 10 张图的文章 = 11 次计数，600/分钟只够约 **50 次浏览/分钟/IP** ——
   在公司 NAT、校园网，或 CDN 回源 IP 未被识别（所有访客共用一个出口 IP）时，正常读者会成片看到 429（AGENTS §7.44）。
2. **站点在 CDN 或大 NAT 后面时，这两个值都要往上调**；调之前先确认 `VANBLOG_TRUST_FORWARDED_HEADERS`
   （默认 `auto`：只有对端是回环/私网时才采信转发头 —— 一体式部署正好如此），
   否则所有访客会挤在少数几个 CDN 出口 IP 的桶里（AGENTS §7.55 F 段）。

## 8. 数据库侧的开销（不在上面那些 HTTP 数字里，但决定了能扛多少）

每单位业务动作打到 Mongo 的命令数，用 mongod 的逐命令计数器或驱动的 `monitorCommands` 实测
（方法与两个"假绿"陷阱见 AGENTS §7.48、§7.55 I 段）：

| 动作 | 改造前 | 现在 |
|---|---|---|
| 一次文章页浏览 | **8.00 条命令 / 4.00 次写** | **~1.0 条 / 0.8 次**（1 浏览/秒）；一轮攒 20 次 = 0.20，攒 100 次 = **0.05** |
| 公开文章列表分页 | 整个集合连正文捞回 Node 再排序切片（docsExamined 106 / returned 53，内存 SORT） | 在 Mongo 里 `$match → $sort → $skip → $limit → $project`（examined 5，无 SORT 阶段） |
| 一次公开搜索的去重 | O(k²)，k ≤ 800 ⇒ 最多 32 万次引用比较 | O(k)（Set） |
| 摘要 + 首图（每篇 × 每次列表请求） | 0.407 ms / 5 篇 | **0.110 ms / 5 篇（3.7×）**；493 KB 长文无 more 标记时 **96×** |
| 整站 JSON 导入 8,772 条 visits | **17,544 次串行命令** | **18 次**（975×） |
| 后台仪表盘 31 天趋势 | 31 次串行 `findOne` | **1 次** `$in` 查询（响应逐字节相同） |
| `/api/public/meta`（全站最热的一次读） | 7 个独立查询**串行**、无缓存 | `Promise.all` + 5 秒进程内缓存 |
| 后台翻一页日志 | 整份日志逐行读 + 逐行 `JSON.parse` | 从尾部按 64 KB 块读，够 2 万行 / 8 MB 就停（52.9 MB 日志 187 ms，与 10.6 MB 基本相同） |

## 9.1 追加实测：caddy 直接发固定页的 ISR HTML（`VANBLOG_CADDY_SERVE_HTML`，默认关）

第 10 节把"caddy 直接发 ISR 生成的 HTML"列为**剩下的最大吞吐杠杆**。它现在**部分实现了**，
而且实现范围比想象的小得多 —— 因为调研发现动态路由有硬阻塞（见下）。数字来自同一台机器、
同一份 53 篇真数据、同一个压测台，所以 A/B 有效（绝对值仍然偏保守）：

| 场景 | 走 Node 反代 | caddy 直发 | |
|---|---|---|---|
| 首页扫描 c=200 × 500 | 279.8–316.1 rps，p50 131–143，p95 1485–1678，p99 1545–1763 | **1171.0–1246.9 rps**，p50 104–128，**p95 240–366**，p99 296–380 | **3.7–4.5× rps，p95 −78…−84%** |
| 首页扫描 c=50 | 313.3 rps | **932.8 rps** | 2.98× |
| 单请求 `/`（identity） | p50 8 ms | **p50 1 ms** | 8× |
| 单请求 `/`（gzip） | p50 7 ms | **p50 3 ms** | 2.3× |
| 单请求 `/about` | p50 6 ms | **p50 1 ms** | 6× |

500/500 全 200、0 个 socket 错误。复现：

```bash
node scripts/benchmark/loadtest.cjs --base http://127.0.0.1:18080 --profile home --c 200 --n 500
node scripts/benchmark/loadtest.cjs --base http://127.0.0.1:18080 --profile latency --paths /,/about,/api/public/meta --n 20
```

⚠️ **两条必须一起读的代价**（这也是它默认关的原因）：

1. **开了以后这 6 条路径完全不受限流**：请求根本不进 Nest，所以不消耗 `VANBLOG_RATE_LIMIT_PER_MIN` 预算、
   也不被任何限流器拦住。而**镜像里的标准 caddy 2.11.4 没有任何限流模块**
   （`caddy list-modules | grep -ci 'rate.?limit'` → **0**；要限流得用 xcaddy 自编 `mholt/caddy-ratelimit`）。
2. **只在 ISR 是 `onDemand` 模式时生效**：`delay` 模式下页面新鲜度 100% 靠流量驱动
   （cron 与保存触发的重渲染风暴在 delay 模式下都被挡掉），直发会让页面**永久冻结**。
   所以 provider 只在 `VANBLOG_CADDY_SERVE_HTML=true` **且** 模式是 onDemand 时才写哨兵文件，
   并每 60 秒对账一次（模式变了会自动摘掉，不用重启）。

**为什么动态路由（`/post/*` 等）明确不做** —— 五条阻塞全部在活体真数据栈上证过，不是推理：

- **删掉的文章的 HTML 会永远留在磁盘上**：软删 + `res.revalidate` 之后，Next 从**内存**里的 notFound 记录回 404，
  而那个 78,830 B 的 HTML 文件不会被删（next 14.2.35 的 `file-system-cache.js` 里没有任何 `unlink`）
  ⇒ **caddy 会无限期地用 200 提供已删除的内容**。
- **308 与 404 不留任何磁盘产物**：`/post/<数字id>` → 308 到别名（`X-Nextjs-Cache: HIT`，没有文件）；
  不存在的文章 → 404，也没有文件。`file_server` 无法从磁盘还原状态码。
- **notFound 只在内存里**（证过：MISS→HIT 且磁盘零写入）。
- **加密文章的明文会留在磁盘上**，直到重渲染风暴重写它（证过：3,081 字明文 → 剥离后的 43,112 B 文件）。
  窗口 = 改动到风暴完成：onDemand 下秒级、每小时 cron 兜底、**delay 模式下无上界**。
- 因此代码里砌了一堵**自带解释的墙**：模板形状的用例里，任何人往那 6 条之外加路径都会抛错并点名这三个阻塞，
  而不是给一个裸 diff。要扩大范围，得先在服务端做出"notFound/重定向时把文件删掉"的语义。

## 10. 已知边界与下一步（按性价比）

1. **caddy 直接发 ISR 生成的 HTML**：✅ **6 个固定页已实现**（`VANBLOG_CADDY_SERVE_HTML`，默认关，见第 9.1 节的实测与两条代价）。
   **动态路由仍未做**，因为调研证明了硬阻塞（删除的文章的 HTML 永不删、308/404 不留产物、notFound 只在内存里）；
   要扩大范围，得先在服务端做出"notFound/重定向时删掉文件"的语义，然后再评估。
2. **打开 cluster**（`VANBLOG_CLUSTER_WORKERS`，默认 1）：代码与守卫都铺好了（cron / 子进程 spawn / 启动清洗 /
   首轮渲染都限定主实例，限流与连接池按 worker 数摊薄），但 **N>1 从未真跑过**，而且内存随 worker 数近似线性增长
   （与"占用更低"是相反的取舍）。打开前必须自己压一遍。
3. **AVIF 缩略图**（现在是 webp）：sharp 0.35 支持，同质量通常再省 20–30% 字节，需要 `<picture>` 回退。
4. **前台资产还能再减**：全局 CSS 里 apple 皮肤 46 KB + markdown 专用表约 27 KB，对 `/link`、`/tag`、`/timeline`
   是死重 —— 被 Next 的 pages router 挡着（只允许在 `_app` 引第一方全局 CSS，三种绕法都被编译器拒），
   要等 Next 大版本或打 patch。字体自托管同理（现在每页请求 3 次字体 CSS、woff2 下载 2 次，
   其中一次来自站点数据里那份重复的 `@font-face`）。
5. **站点数据里的第三方脚本**（不是代码问题，但对首屏影响最大）：一个 798 KB 的 MathJax（公式已由 KaTeX
   服务端渲染，纯重复）、gtag 与百度统计各加载两次、两个 51la 属性且开着 `screenRecord`、一个超时的计数器图片。
   在后台「定制化」里删掉即可，见 AGENTS §7.38.2。

这一页记录 VanBlog 在服务端做的安全约束，以及部署时可以用环境变量调整的几个开关。做过多轮完整审计（认证/权限、上传与文件、注入与数据暴露、功能正确性四个方向，2026-09 又加了针对匿名写接口与备份链路的一轮），下面是结论。

<!-- more -->

## 上传

- **图床只接受真图片**：按文件**内容**（魔数 + 解码）判定类型，不看客户端给的后缀和 MIME。`.html` / `.svg` / 伪装成 png 的任意文件一律 400。原因：`/static/img/**` 与站点同源且匿名可读，一个能存进去的 HTML 就是存储型 XSS（可偷后台 token）。非图片请走 [附件管理](../features/attachment.md)——附件对 html/svg/js 等类型强制下载并带 `nosniff`。
- **体积上限**：图片 50MB、自定义页面 200MB、附件 200MB、旧版 JSON 备份 200MB、整站备份恢复 8GB（落盘，不进内存）。
- **像素上限 4000 万像素（40MP，≈8K）**：隐写水印需要把整图解码成 RGBA，而流水线会同时持有好几份（缩放、可见水印、隐写、webp/avif、缩略图），`UV_THREADPOOL_SIZE=16` 又允许 16 个并发解码，超大图会瞬间吃掉上 GB 内存。40MP 解码后约 160MB RGBA —— ⚠️ 这是**内存预算，不是画质标准**：45/61MP 的相机原片会被拒（提示「图片尺寸过大（WxH）」），但反正上传后也会按长边 1920 缩小，所以损失的是"原分辨率存档"，不是页面画质。建议先在本地导出成 ≤40MP 再传。sharp 的 `limitInputPixels` 也被钉到同一个数字（库默认 268MP，比业务上限宽 6.7 倍，而 `image-size` 读不出尺寸时会**放行**，那条路上就只剩 sharp 这一层）。
- **落盘文件名有两层防护，不再依赖第三方库的默认行为**：生产者一侧净化文件名（去分隔符、控制字符、引号、前导点），落盘前再做一次**容器化校验**（`path.resolve` + `path.relative` 确认结果仍在图片目录内），校验发生在写入**之前**。早先唯一挡住路径穿越的是 busboy 在 `preservePath` 未开时会做 `basename()` —— 那是**依赖的默认值**，一个配置改动或换一个上传库就没了。删除路径同样有容器化校验，越界时**大声 WARN 并跳过删除**（删除是不可逆的，而它要删的文件名来自数据库记录，JSON 导入那条路能写进去）。
- 整个静态目录都带 `X-Content-Type-Options: nosniff`；可执行/可渲染的文本类型（html、svg、js、css…）无论在哪个子目录都强制下载。
- 图片与缩略图缓存：`public, max-age=3600, stale-while-revalidate=604800`（不用 `immutable`，因为「替换图片」是同名覆盖）。

## 下载与导出

- 「导出全部图片 / 导出全部附件」的归档**不再放在静态目录**，改存 `backup.path/export/`，只能通过带登录态的 `GET /api/admin/export/archive?name=` 下载，下载完即删除。以前归档在匿名可读的 `/static/export/` 下、文件名只有日期，任何人都能猜出来把整站图片和附件拖走。
- 整站备份归档同样在静态目录之外，`/static/export/`、`/static/tmp/`、`/static/upload-tmp/` 一律匿名 403。
- 旧版 JSON 导出改成系统临时目录 + 无论成败都删除。

## 认证

- **登录防爆破默认开启**：5 次失败 / 300 秒（后台「登录设置」**只能整体开关** —— 🔴 `maxRetryTimes` / `durationSeconds` **没有表单字段**，代码读设置里这两个键、大于 0 才生效，所以要改阈值只能直接改库）。只统计**失败**次数，登录成功即清零——以前的实现把成功登录也算一次，正常用户一分钟内登录几次就会被锁在门外。
- **防爆破计数按「可信客户端 IP」分桶**（`VANBLOG_BRUTE_FORCE_IP_SOURCE`，默认 `trusted`）：
  一体式部署里 caddy 从回环拨过来，如果按套接字地址计数，**所有访客共用一个桶**——
  实测 5 个请求就能把带正确密码的真管理员锁在门外，且每 5 分钟可续期（等于后台永久 DoS）。
  现在登录、评论频率、加密文章解锁三处计数都取可信判定后的客户端 IP（`auto` 模式下
  caddy 追加的 XFF 最右一跳；客户端伪造的头排在它左边，既绕不过也栽赃不了）。
  反代是**覆盖**而不是追加 XFF 的部署，用 `VANBLOG_BRUTE_FORCE_IP_SOURCE=socket` 退回旧行为。
- **体量类限流**（全局/静态/公开写/初始化）同样按可信客户端 IP 分桶：
  `VANBLOG_TRUST_FORWARDED_HEADERS` 默认 `auto` = 只有对端是回环/私网时才采信
  `X-Forwarded-For` 的**最右一跳**；对端是公网地址一律用套接字地址。
  这堵掉了「每个请求换一个 `cf-connecting-ip` / `x-real-ip` 就绕过限流」
  （这些头客户端可控，caddy 不剥）。CDN/隧道**直连源站**时设 `always`，见 [反代](../reference/reverse-proxy.md)。
- **登出需要有效 token**：`POST /api/admin/auth/logout` 挂了 TokenGuard——以前匿名请求
  就能触发 `logout` 流水线事件（管理员写的自定义代码被未认证调用方启动）。
- 空密码一律拒绝：改密码、建/改协作者、「忘记密码」恢复通道都会校验用户名与密码，避免把密码哈希写成空串（空哈希曾经能用空密码登进来）。
- **「忘记密码」的恢复密钥校验是失败关闭的**：内存里读不到就回落 `<日志目录>/restore.key`（0600，主实例启动时写），两边都拿不到可用字符串就**拒绝**并打一条能照做的 ERROR（点名那个文件与可能原因），绝不把"没有密钥"当成"密钥匹配"。多进程（`VANBLOG_CLUSTER_WORKERS>1`）时 worker 也走这条文件回落，所以 cluster 模式下恢复通道照常可用（与初始化密钥同一套先例）。
  ⚠️ 早先的形状值得记一句，因为它解释了"为什么要写类型检查"：缓存缺失时返回的是 `{}` 而不是 `undefined`（登录防爆破窗口依赖这个返回形状，所以不能改它的语义），而比较用的是松散 `!=` —— 在 JS 里 `"[object Object]" != {}` 是 **false**（对象先被转成原始值），于是"没有恢复密钥"与"密钥正确"不可区分：匿名 POST 一个 `{"key":"[object Object]", …}` 就能改掉 `id:0` 管理员的用户名与口令，并连带吊销真管理员的令牌。单进程部署只是**恰好**安全（写密钥发生在第一个 `await` 之前），多进程时每个 worker 都处于可绕过状态。
  ⚠️ 反直觉的一条：换成常量时间比较**并不能**修好它 —— `safeEqual` 自己会把两边 `String()` 化，`safeEqual('[object Object]', {})` 是 **true**，同一个陷阱换了顶帽子。真正堵住洞的是比较**之前的类型检查**。新代码取凭据一律用 `CacheProvider.getString()`（缺失、非字符串、短于下限都返回 `null`），不要用 `get()`。
- **「忘记密码」恢复接口现在有专用限流桶**：每 IP 每 10 分钟 **5 次**，超限返回 **429** 并带
  `Retry-After` 头（脚本读这个头就行，不用解析中文消息），成功后计数清零。
  限流判定放在**读密钥之前**，所以被拦下的尝试连密钥文件都不会去读。
  ⚠️ 它复用 `VANBLOG_INIT_LIMIT_PER_10MIN`（没有新变量），调大那个值会把初始化与恢复两处一起放宽。
  计数用的是**套接字地址**口径的客户端 IP（与登录、评论、解锁那几个"防爆破"计数一致），
  多进程时按 worker 数摊薄。
- **改口令 / 走恢复流程后，旧令牌在响应返回之前就已经失效**：吊销是 `await` 的，
  而且新令牌写库也是 `await` 的。以前的形状是"写库不 await + 吊销放进 `setTimeout(…, 1000)`"，
  于是登录后立刻改密码时，那个还没落库的新令牌可能躲过吊销（旧的都失效了它还活着），
  而进程在这一秒内退出则吊销完全不发生。⚠️ 吊销范围包含**全部 API Token**
  （API Token 的 `userId` 是 666666，落在 `$ne:0` 这个条件里），所以改完密码要重新签发 Token。
- 协作者读不到分类的加密密码（`GET /api/admin/category/all?detail=true` 会对协作者脱敏）。
- 权限判定出错时**拒绝**（以前是放行）。
- **初始化窗口**：未初始化期间匿名初始化接口默认要求[初始化密钥](../guide/init.md#初始化密钥setup-key)
  （`VANBLOG_INIT_REQUIRE_SETUP_KEY`，新版默认开），或用零接触初始化（`VANBLOG_ADMIN_USER` 等）
  让窗口根本不存在。
  ⚠️ 三条 init 接口里有**一条是例外**：`POST /api/admin/init/upload`（向导里传 logo / favicon）
  **不要密钥**，而且是故意的 —— 向导的上传组件手里没有密钥（密钥输入框要等提交 `/init` 被 400 拒了
  才出现）。所以未初始化期间匿名可以往图床传图，爆炸半径被三层限制住：只在 `checkHasInited()` 为假时
  开放、init 桶限流 5 次/10 分钟/IP、以及上传自身的类型与大小校验 —— **不能**用它接管站点。
  想彻底关掉这个窗口就用零接触初始化：站点在开始监听之前就已初始化，这条接口永远回「已初始化」。
- **多进程下初始化 / 恢复由数据库锁互斥**：`VANBLOG_CLUSTER_WORKERS>1` 时，`POST /api/admin/init`
  与 `POST /api/admin/init/restore` 共用一把 **Mongo 里的 TTL 锁**（集合 `vanblog_locks`、锁名
  `init-restore`）。抢不到锁的一方得到 **409**，消息以「已经有一个初始化/恢复正在进行（由另一个进程持有锁），请等它结束…」开头，
  后台会原样显示这句话。
  - 为什么需要它：以前只有"每进程一个布尔量"，两个 worker 同时收到请求就会**都**通过检查 ——
    两个 `/init` 会造出**两个 `id:0` 管理员**（此后"谁是管理员"取决于查询返回顺序），
    两个 `/init/restore` 会对同一个库并发做"临时集合 + 原子替换 + 重建索引"，得到半新半旧的库。
  - 进程被硬杀（OOM / `kill -9`）时 `finally` 不会执行，所以锁**会过期**：默认 30 分钟
    （`VANBLOG_INIT_LOCK_TTL_MINUTES`，夹取 1–1440，`0`/负数/垃圾值回落默认，**不会变成永不过期**），
    过期后可以被接管，不会把站点永久卡死。
  - 锁后端不可用时（连接还没就绪等）**降级**为只用进程内闸门，并且**每进程 WARN 一次**说明自己降级了
    —— 静默降级的锁是最危险的失败方式。单进程部署不受影响。
  - 锁**不放在 `settings` 集合**里，因为那个集合会被整站备份导出/恢复；放在独立的 `vanblog_locks`
    集合里就不会在两套安装之间漂移。边界：这个集合也会随整站备份一起导出，但恢复出来的锁要么已过期
    可接管、要么最多让目标站在 TTL 内不能再次初始化 —— 而恢复成功后站点已经初始化，这两条接口本来就关了。

## 请求参数

- 全局净化中间件会递归删掉请求里以 `$` 开头的键（Mongo 操作符）以及 `__proto__` / `constructor` / `prototype`。以前 `?category[$ne]=x`、`?path[$regex]=^/bl` 这类查询对象会被直接塞进 Mongo 过滤器。
- **multipart 的文本字段现在也过净化**：全局净化中间件跑在 `json()` 之后、但在 multer 的
  `FileInterceptor` **之前**，所以上传请求里的普通字段（不是文件）以前是不经净化的 ——
  `$` 前缀键与原型键能活着进到 handler。现在改由一个**全局管道**做净化：Nest 的顺序是
  中间件 → 守卫 → 拦截器 → **管道** → handler，管道是唯一跑在 multer 填好 `req.body` 之后的位置。
  它覆盖全部 10 个 multipart 入口（分布在 8 个 controller），对已经净化过的 JSON 体是幂等的。
  ⚠️ 今天没有任何路由把 multipart 字段塞进数据库查询，所以这不是一个可利用的洞，
  而是"等第一个这样的调用方出现之前就把它堵上"。
- 所有进入 `$regex` 的用户输入都会转义并限长 200 字符，搜索还带 5 秒 `maxTimeMS`。以前搜 `(`、`[`、`*`、`a{2,1}` 会让公开搜索接口直接 500，`(a+)+b` 这类模式还能造成灾难性回溯。
- 加密文章不会通过搜索、RSS、`POST /api/public/article/:id`（输密码解锁）泄露：这三处以前各有一条缝。
- **JSON 请求体限额**：全局默认 **1mb**，只有后台四个内容前缀保留 **50mb** ——
  `/api/admin/article`、`/api/admin/draft`（正文可以内嵌 base64 图片）、`/api/admin/customPage`
  （整页 HTML/JS 当字符串提交）、`/api/admin/pipeline`（脚本正文），而这四个都在登录与权限之后。
  以前 `express.json({limit:'50mb'})` 挂在**每一个**路由上：登录、公开评论、访客计数这些
  **匿名可达**的接口都敞着 50MB 的解析上限（内存风险 + 现成的 DoS 面）。
  超限返回 **413**（实测 1.17MB 打登录与公开评论就是 413）。可用 `VANBLOG_JSON_BODY_LIMIT` /
  `VANBLOG_JSON_BODY_LIMIT_LARGE` 调，非法值回落默认。
  ⚠️ 图片上传、整站备份恢复、JSON 导入走的是 multipart，**不经过这个解析器**，
  它们的上限见上面「上传」一节（50MB / 8GB / 200MB），改这两个变量不会影响它们。
- 🔴 **「Mongoose 丢掉值为 `undefined` 的查询条件」这个陷阱，本仓库已经踩到第五例**，
  规律是一样的：一个本该「定位到这一行」的过滤器，因为某个字段的值是 `undefined` 而被静默丢掉，
  退化成 `{}` ⇒ 匹配**自然顺序里的第一行**。五例：
  1. `checkToken`（token 为空 ⇒ 「任意一条未吊销的 token」）—— 造成过**未认证的管理员接管**；
  2. `updateCollaborator`（不带用户名 ⇒ 改掉**任意一个**协作者的口令与权限）；
  3. `PUT /api/admin/customPage`（body 既无 `_id` 也无 `path` ⇒ 改写**第一个自定义页面**的公开 HTML；
     该路由不在超管专属清单里，所以持「所有权限」的协作者可达 —— 等于「一个不含任何标识符的请求
     静默篡改公开站点内容」）；
  4. `DELETE /api/admin/customPage`（不带 `path` ⇒ 删掉任意一页，而 `folder` 类型还会**连带删掉磁盘目录**，
     比第 3 例更具破坏性）；
  5. 分类删除的 `deleteOne({ name })` —— 内联字面量、但**值是变量**，一样会被丢掉；今天不可达
     （路由要求 `:name`），但它的意外兜底（非空分类不许删）只在库里还有文章时成立，
     「安全依赖于路由的形状」不是防护。

  现在写路径统一走 `utils/queryFilter.ts`：`isUsableFilterValue` 拒绝 `undefined`、`null`、空白、
  字面量字符串 `'undefined'`/`'null'`（它们来自 `String(undefined)` 与查询拼接）、`NaN` 与 `{}`；
  接受非空字符串、有限数字（**包括 0** —— 本仓库用 `id: 0` 表示管理员）、布尔（**包括 false** ——
  `{disabled:false}` 是真条件）、Date 与 ObjectId 形状。写操作另有最后一道 `assertSafeWriteFilter`，
  ⚠️ 它抛的是 **500 而不是 400**：走到它说明是**代码**漏了校验，报成客户端错误会让它永久埋在
  「用户又乱传东西了」里。它也拒绝 `null`，因为 `{field:null}` 虽然不会消失，但匹配的是**一批**文档
  而不是「这一行」，属于同一类意外。
  读路径保留各自的判断，**8 处用变量做 filter 的读操作全部审过、无需修改** ——
  每一处都由字面量基座（`$and` / `{deleted:true}`）、`parseNumericId` 对垃圾输入抛错、
  或「`{}` 本来就是『列出全部』的预期语义」三者之一保护着。
- **布尔解析统一成一套，而破坏性操作的确认闸门刻意用最严的那套**：以前仓库里有**五种**布尔口径
  （`process.env.X === 'true'`、`Boolean(process.env.X)`、`checkTrue()`、`isTrue()`、`envBool()`），
  其中 `checkTrue` 与 `isTrue` 在 `"1"`、`1`、`[1]` 上**结论相反**（前者用了松散比较 `s == true`）——
  于是新调用方选哪个工具，决定了 `VANBLOG_X=1` 到底开不开。而 `checkTrue` 恰恰是**整站恢复的确认闸门**：
  `confirm:"1"` 也算「是，覆盖一切」。现在 `isTrue` 是唯一真相源（只认布尔 `true` 与字符串 `'true'`，
  **区分大小写**），`checkTrue` 委托给它并标为 `@deprecated`，恢复闸门**直接点名 `isTrue`**，
  这样将来放宽那个废弃别名也不会连带放宽闸门。
  ⚠️ `envBool` **有意保持宽容**（认 `1`/`yes`/`on`）：环境变量的值是运维在终端里敲的，
  而请求体与库里的值应当严格 —— 这条差别写进了代码注释，防止有人「统一」到错误的方向。

## 出站请求（SSRF）

- 所有服务端抓取外链的地方（导出 md/mdz 时抓远程图片、转移外链图片、扫描文章图片）都走同一套 `fetchRemoteSafely`：**禁用自动重定向，每一跳重新校验**，只允许 http/https，拒绝回环/内网/链路本地地址，抓回来的内容必须是真图片（魔数校验）才会被使用。
  以前只校验第一个 URL，攻击者可以用自己的域名过检再 302 到 `169.254.169.254`（云元数据）或 `127.0.0.1` 的内部服务，把响应体原样带回来。
- **内网判定是在"解析之后"做的，不是对字符串做黑名单匹配。** 早先用的是一组正则（点分十进制 + `::1`/`fc00::/7`/`fe80:`），于是所有 IPv6 过渡形式都能过：`http://[::ffff:127.0.0.1]:2019/`（IPv4-mapped）、`http://[::ffff:169.254.169.254]/latest/meta-data/`、NAT64 的 `http://[64:ff9b::7f00:1]/` —— 它们既不像点分十进制、也不匹配那几条前缀，而**连通性是实测过的**（只监听 127.0.0.1 的服务能被 `net.connect(port, '::ffff:127.0.0.1')` 打到）。现在 IPv4 走 32 位区间判定（补上了 CGNAT `100.64/10`、组播、保留段、三个 TEST-NET、`198.18/15`），IPv6 手工展开成八组再比对（`::`、`::1`、`fc00::/7`、`fe80::/10`、`ff00::/8`、`2001:db8::/32`、Teredo、两个 NAT64 前缀），而三种内嵌 IPv4 的形式（mapped `::ffff:0:0/96`、compatible `::/96`、6to4 `2002::/16`）会**拆出里面的 IPv4 再判一次**。⚠️ 还有一条兜底原则：**解析不出来的输入一律判不安全**——像 `gggg::1` 这种含冒号但不是合法 IPv6 的字面量，早先会掉进"域名"分支被判成公网。
- **校验与连接之间不做第二次解析**（否则短 TTL 域名可以第一次答公网、第二次答 `127.0.0.1`，即 DNS rebinding）。连接走一个自定义 agent，它的 `lookup` 钩子**钉住校验时解析出的那个地址**（Host 头与 SNI 仍是域名，所以证书校验不受影响）；如果从校验过的结果里挑不出可用地址，请求**直接失败**而不是回落到 Node 自己的解析——回落等于悄悄把钉住这件事取消掉。
  ⚠️ 实现上有个坑值得记：Node 20+ 默认开 `autoSelectFamily`，会以 `all: true` 调 `lookup`，回调拿到的是**数组**而不是单个地址；只按 `(err, address, family)` 写的话，**每一次外链抓取都会失败**（这个 bug 是被端到端钉子抓到的，单测发现不了）。
- **默认只允许连 80/443**（`VANBLOG_REMOTE_FETCH_ALLOWED_PORTS`，逗号分隔）。写错值不会变成"全部放行"：没设/空串/一个合法项都没有都回落默认，单个非法项被忽略、其余照常生效。⚠️ 这是行为变化——图片挂在非标准端口的站点，外链转存与导出抓图会开始失败，报错里写了怎么配。地址判定在端口判定**之前**，所以 `http://127.0.0.1:3000/` 报的是"内网地址"（真正的原因）而不是"端口不允许"。
- 可达性与影响范围：`POST /api/admin/export/markdown` 在协作者白名单里，`fetchRemoteSafely` 的两个调用方也都在协作者可达的路由上，所以**最低权限的协作者**就能触发。影响是**盲打**（靠状态码/超时差异探内网端口、对内部服务发 GET 造成副作用），不是数据外泄——只发 GET，且回来的内容要先过图片魔数校验才会被使用。
- Caddy 的按需证书回调 `/api/admin/caddy/ask` 只批准本站域名（`siteInfo.baseUrl`、HTTPS 设置里的域名、已登记的 subjects）。以前任何非 IPv4 的域名都会被批准，别人把域名指过来就能让本站为它申请证书。

## 口令存储：scrypt（登录时自动迁移）

管理员与协作者的口令以前是 `sha256(sha256(username + 浏览器端派生值) + salt + sha256(username + salt))`。
纯 sha256 是**快哈希**：拿到库（或整站备份）之后可以用 GPU 每秒试几十亿次。现在改成 **scrypt**
（`N=16384, r=8, p=1`，每次校验要吃 16MB 内存），存储格式自描述：

```
scrypt$16384$8$1$<salt base64>$<hash base64>
```

- **迁移是透明的**：校验函数同时认新格式与旧格式，登录成功时顺手把旧哈希升级成 scrypt
  （`UserProvider.updateSalt()` 本来就每次登录轮换盐）。用户不需要改密码，也不用停机跑脚本。
- 客户端不用改：scrypt 的输入仍然是浏览器端派生出来的那个值。
- 新建用户、改密码、建/改协作者、「忘记密码」恢复通道都直接写 scrypt。
- 只有一处仍是旧格式：`washUserWithSalt()`（把更老的「无盐」数据洗成带盐的）。它的输入是
  **上一代服务端哈希**，拿不到浏览器端派生值，没法直接换；等该用户下次登录成功就会自动升级。
- 校验时会检查 scrypt 参数上限（`N ≤ 2^20`、`128*N*r ≤ 64MB`）：库被改过也不至于构造出
  一个让进程 OOM 的哈希。
- 空口令一律拒绝（空哈希曾经等于「空密码可登录」）。

### 文章/分类的访问密码也是 scrypt（且不可找回）

同一轮里，**文章与分类的访问密码**从明文存储改成了同一套 scrypt：

- **密文永不下发**：所有会序列化成响应的形状都把 `password` 换成布尔 `hasPassword`
  （哈希也不是"可以下发的东西"——它一样能被离线爆破）；
- **表单语义随之改变**：更新时**留空 = 不修改**，解除加密必须显式勾「清除密码」开关
  （同时给密码又勾清除 = 400，两种意图冲突）；
- **历史明文自动收敛**：启动时注册了一个幂等清洗任务，把库里的存量明文洗成 scrypt；
  整站备份/恢复走 `toObject()` 原样进出，不会被二次哈希；
- ⚠️ 代价要说清楚：**忘记访问密码从此无法找回**（以前明文时后台还能翻库看），
  只能在后台显式清除/重设。产品细节见 [加密文章](./encrypt.md)。

## 后台渲染日志：ANSI 转 HTML 必须转义

后台「日志管理 → 系统日志」把日志文本经 `ansi-to-html` 转成带颜色的 HTML，再用
`dangerouslySetInnerHTML` 塞进 `<code>`。这个库的 `escapeXML` **默认是 `false`** ——
也就是日志里的 `<`、`>`、`&` 会原样成为标签。而日志里完全可能出现访客可控的字符串
（404 的路径、上传的文件名、评论作者、子进程输出里的 URL），于是这就是一条
**存到后台的 XSS**：谁打开那个页面谁中招，而后台 token 就放在 localStorage 里，
等于把管理员会话交出去。

现在组件显式用 `new convert({ escapeXML: true })`：ANSI 颜色照常渲染（这本来就是它的用途），
尖括号变成实体。测试里除了断言源码写了这个选项，还**用真库跑了一遍**：
`<img src=x onerror=alert(1)>` 必须变成 `&lt;img …`，同时默认配置的对照组必须仍然漏出真标签
（证明这个修复不是白改的）；另有一条断言盯着"全后台只允许这一处
`dangerouslySetInnerHTML`"，以后谁再加第二处就会被逼着想清楚"这里的数据是谁写的"。

## 限流

| 范围 | 默认 | 环境变量 |
| --- | --- | --- |
| 登录（按 IP） | 同可信 IP 5 次 / 300 秒，超了临时拒绝 | — |
| 登录（全局失败速率） | 全局每分钟失败 **>120** 次后，给**所有**登录加延迟（每超一倍 +500ms，封顶 3 秒）。⚠️ **加延迟不是封号** | `VANBLOG_LOGIN_GLOBAL_FAIL_PER_MIN` / `VANBLOG_LOGIN_THROTTLE_MAX_MS` |
| 登录（网段白名单） | 默认不限制；配了就只有这些网段能登录，其余 **403** | `VANBLOG_ADMIN_LOGIN_ALLOW_CIDR` |
| 加密文章解锁（按 IP × 文章） | 同可信 IP + 同文章（id 归一化）10 分钟 20 次 | — |
| 加密文章解锁（按文章全局） | **每篇** 10 分钟 500 次，与来源 IP 数无关 | `VANBLOG_UNLOCK_GLOBAL_BUDGET_PER_10MIN` |
| 「忘记密码」恢复 | 10 分钟 5 次（与 init 共用同一档阈值） | `VANBLOG_INIT_LIMIT_PER_10MIN` |
| 图片隐写检测 | 每 IP 每分钟 **10** 次（这条路由**协作者勾了任意一项权限**就能调，而单次检测要吃几百毫秒 CPU 与几百 MB 内存） | — |
| 发表评论 | 10 分钟 N 次 + 每天 50 次 + 同内容 5 分钟 1 次 | 后台「评论设置」 |
| `/api/admin/init*` 的**写请求** | 10 分钟 5 次（GET/HEAD/OPTIONS **不计入**，见下） | `VANBLOG_INIT_LIMIT_PER_10MIN` |
| `/api/public/**` 写操作 | 每分钟 30 次 | `VANBLOG_PUBLIC_WRITE_LIMIT_PER_MIN` |
| 🔴 `/api/public/category` 与 `/api/public/tag`（匿名聚合列表） | 每分钟 **60** 次（独立桶，命中后**仍计入**全局兜底，取最严的那个） | `VANBLOG_PUBLIC_LIST_LIMIT_PER_MIN` |
| 静态资源 `/static/**` | 每分钟 6000 次（全局 ×10 的独立桶） | `VANBLOG_STATIC_LIMIT_PER_MIN` |
| 全局兜底 | 每分钟 600 次 | `VANBLOG_RATE_LIMIT_PER_MIN` |

覆盖面与设计原则：

- **`/static/**`、`/rss/**`、`/sitemap/**`、`/swagger*` 也在限流与安全响应头之内**：
  这些响应以前在 Nest 中间件安装**之前**就结束了，等于完全绕过限流（`rl-static-<ip>`
  那个独立桶是永远执行不到的死代码）也拿不到 `X-Frame-Options` 等安全头。现在 main.ts
  在静态层之前挂了一个前置限流器（路径匹配与 staticGuard 同口径：**先百分号解码再比**，
  `%2Fstatic%2F…` 之类写法溜不过去），独立桶真正生效。
  🔴 **2026-09-22 补：那道前置门控的路径比较此前是大小写敏感的，而 Express 的静态挂载前缀匹配默认大小写不敏感**
  ⇒ 把 `/static/` 写成 `/STATIC/` 就能绕过它、回到"静态资源完全不限流"的状态（同时也拿不到那几个安全响应头）。
  现已改为大小写不敏感比较，并有一条仓库级横切守卫盯着这个形状（见下）。
  ⚠️ **注意"要不要解码"取决于下游是谁**：静态层的下游 `serve-static` 会解码，所以这里**必须**解码；
  而限流分档的下游是 Express 路由，它用的是**未解码**的 `req.path`，所以那一侧**必须不解码**。
  两处口径故意不同，不要"统一"它们。
- 🔴 **路径前缀比较的大小写口径有一条横切守卫**（`pathPrefixCaseDrift.spec.ts`）：
  它区分**请求路由判定**（必须大小写不敏感，因为 Express 的路由与静态挂载就是大小写不敏感的）
  与**数据形状校验**（大小写敏感是正确的，例如校验容器内文件路径、归档成员名、应用自己生成并存库的 URL）。
  这个形状曾在四个不同模块各出现一次（静态目录守卫、前置限流门控、管理响应的 `no-store`、限流分档），
  而每次只修被发现的那一处 ⇒ 守卫的意义是**第五处长出来时立刻变红**。
- **`/api/public/category` 与 `/api/public/tag` 有 5 秒的结果缓存**（`VANBLOG_PUBLIC_LIST_CACHE_MS`，上限 60 秒）：
  这两个匿名端点此前**既无缓存也无单飞**，每次请求都全表捞取；现在同样的 key 在 TTL 窗口内最多取一次数，
  单请求成本降了约 6 倍，**响应体逐字节不变**。`/api/public/tag/<标签名>` 复用同一份缓存条目
  （不按标签名建键 —— 标签名是攻击者可控的，按名建键等于开一个无界键空间）。
  ⚠️ **行为变化**：发文/改文/删文后，这两个端点**最多 5 秒**才反映变化；而前台本身是 ISR
  （文章页的再验证是天量级），所以这个窗口比用户已经体验到的陈旧窗口紧得多。
- **容器内部回环直连放行**（前台 SSR、waline、ISR 触发都要高频调公开接口）。判据要求
  「socket 是回环 **且** 请求里没有 `X-Forwarded-For` / `X-Real-IP`」—— 经过 caddy/nginx
  转发的一定带转发头，所以反代后面的真实客户端不会被误放行。
- **fail-open**：限流组件自己抛错时放行。宁可少挡一次，也不能因为一个计数器把整站变成 500。
- 🔴 **`/api/admin/init*` 按「方法」计数，不按「路径落在前缀里」计数**（`68727ae5`）。
  此前是一律计数，于是任何"用 `GET /api/admin/init` 判断站点是否已初始化"的监控/脚本/探针都会**白吃配额**：
  活体实测 **3 次探测就把 5 次/10 分钟吃光**，之后**真正的初始化与灾难恢复被 429 锁死最长 10 分钟**
  ——恢复窗口被自己的监控吃掉，而这正是最不该发生的事（后台初始化页甚至专门写了"页面加载时不发探测请求"的注释来绕开它）。
  现在 `GET`/`HEAD`/`OPTIONS`（RFC 9110 的安全方法）不计入，**配额一点没放宽**：这个前缀下只有三个路由、
  **全是 POST**（`/init`、`/init/upload`、`/init/restore`），匿名爆破初始化与"反复上传大归档做放大"照旧计数。
  ⚠️ 刻意选"非安全方法"而不是"精确路径白名单"：白名单在**将来有人往这个前缀下加写路由**时会**静默失效**（放行），
  而方法规则会自动覆盖它 —— 失败方向很重要，**限流过松比限流过紧更糟**（有测试钉住）。
  ⚠️ 仍然在**请求进入时**计数、不等响应：这个桶要防的正是"反复上传几 GB 的归档"，
  等响应出来再记账，那次上传的 CPU 与 I/O 已经花掉了。所以"只给非 404/405 的响应计数"那种修法在这里是**错的方向**。
  ⚠️ **运维指引**：别拿 `/api/admin/init*` 当健康/状态探针，用 **`/api/public/health`**（不在这个桶里）；
  确需反复试恢复口令时临时调高 `VANBLOG_INIT_LIMIT_PER_10MIN`（⚠️ 它**同时**管着「忘记密码」恢复接口，调大会一起放宽）。
- 多进程（cluster）时各档阈值按 worker 数**摊薄**：计数器是每进程内存的，不摊薄等于
  把预算悄悄放宽 N 倍。
- 计数器表有 20000 个 key 的硬上限 + 定期清扫（旧实现超限会整表清空，攻击者可以用一次性
  key 把别人的计数一起清掉）。

命中限流返回 `429` 并带 `Retry-After`。

## 其它加固

- **安全响应头**（caddy 模板对**所有**响应下发，Nest 中间件对 `/api/**`、`/static/**` 也下发；
  `set` 是覆盖不是追加，所以不会重复）：`X-Content-Type-Options: nosniff`、
  `X-Frame-Options: SAMEORIGIN`（不是 DENY：后台要 iframe 同源的 waline `/ui`）、
  `Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`，并隐藏 caddy 的 `Server` 头。
- **HSTS**（`Strict-Transport-Security: max-age=31536000`，可用 `VANBLOG_HSTS_MAX_AGE` 调，写 `0` = 不发）：
  **只加在 443 上** —— 80 上不发（浏览器按 RFC 6797 会忽略明文连接上的 HSTS），降级配置（证书校验不过时
  用的那份自签配置）**故意不发**，因为在证书本来就不可信的路径上要求「一年内只用 HTTPS」等于把站长锁在站外。
  没有加 `includeSubDomains` 与 `preload`：前者会波及同域名下别的子域（可能是别人的服务），
  后者一旦提交到浏览器预加载列表就**很难撤回**。
  ⚠️ **代价要如实知道**：带 HSTS 的域名在 max-age 窗口内**无法退回纯 HTTP**，而且证书续签失败时浏览器是
  **硬失败**、不给「仍然前往」。所以务必确认证书目录真的持久化了（`./vanblog.sh doctor` 会查这一项，
  k8s 部署尤其容易漏挂 caddy 的两个卷）。
- **`pageSize=-1` 收敛**：公开文章列表以前允许任何人一次性把**全部文章连正文**拉走
  （一个现成的拖库 + 打爆内存按钮）。现在只有内部调用（回环直连，或带
  `x-vanblog-internal: <VAN_BLOG_INTERNAL_TOKEN>`）可以，其它一律夹到 `MAX_PAGE_SIZE`（**100**）。
  前台静态生成走的是容器内回环，一体式部署不需要任何配置；前后端分离部署时给两边配同一个
  `VAN_BLOG_INTERNAL_TOKEN` 即可。
- **API Token 有效期**：原来是 **100 年**（等于永不过期，泄露一次长期有效）→ 改成默认 1 年 →
  本轮再改成默认 **90 天**（`VANBLOG_API_TOKEN_TTL_DAYS`，夹在 1–36500）。理由是 Token **等价于超级管理员**
  （签的就是 `id: 0`，不受协作者权限约束），有效期就是「泄露之后攻击者能用的时长」上限；
  90 天短到「泄露会自然过期」、长到「正常的自动化集成不用每月去后台重签」。
  已签发的 token 不受影响（各自的 `expiresIn` 已经写在库里），要立刻收紧就在后台吊销重签。
- **文章解锁的密码比较改成常量时间**（原来的 `!==` 会因短路泄露长度/前缀信息），
  并且同时支持明文（历史数据）与 scrypt 哈希。
- **CSP：只加了三条非取数指令，覆盖面也不大，别高估它**。现在下发的是
  `frame-ancestors 'self'; object-src 'none'; base-uri 'none'`：
  - `frame-ancestors 'self'` 与已有的 `X-Frame-Options: SAMEORIGIN` 同义（后台 iframe 同源的 waline
    `/ui` 是**我们去框它**，属 `frame-src`，不受影响）；
  - `object-src 'none'` 安全，因为正文白名单里有 `iframe` 但没有 `object` / `embed` / `applet`；
  - `base-uri 'none'` 安全，因为 `<base` 在前台与后台都是零命中。
  ⚠️ **它只作用于 `/static/`、`/rss/`、`/sitemap/`、`/swagger` 这几个 pre-Nest 前缀** ——
  前台是独立的 Next 进程、后台是独立的静态包，**都不经过这个中间件**。
   ⚠️ **（2026-09-20 更正）上面这条"只覆盖四个前缀"仍然成立，但"全站没有 CSP"已经不成立了**：
   全站页面级 CSP 现在落在 **caddy 层**（唯一能看到每一个响应的地方），由 `VANBLOG_CSP_MODE` 控制，
   **默认 `report`** —— 发的是 `Content-Security-Policy-Report-Only`，**只报告不拦截**。
   默认不直接 `enforce` 是有意的：全站策略一旦强制生效，打坏的是"站长自己加的第三方脚本 / 字体 / 统计"
   这类我们看不见的东西，所以先让它报告一段时间。策略是**生成配置时注入**到既有的全局 `headers` handler 里的，
   两个模板文件都没被改（`off` 模式下生成结果与模板逐字节相同），主模板与降级模板因此不会漂。
   内置策略：`default-src 'self'`；`script-src 'self' 'unsafe-inline'` + googletagmanager + 百度统计；
   `style-src 'self' 'unsafe-inline'` + zeoseven 字体 + jsDelivr；`img-src * data: blob:`（正文可以嵌任意外链图）；
   `font-src`；`connect-src 'self'` + GA 各域 + 百度；`frame-src 'self' https:`（正文白名单允许 iframe 嵌
   B 站/YouTube）；`frame-ancestors 'self'`、`object-src 'none'`、`base-uri 'none'`、`form-action 'self'`
   （正文白名单里没有 `form`，所以这条安全）。`upgrade-insecure-requests` **故意不加**（它会打坏纯 HTTP 站点，
   而 HTTPS 跳转已由 caddy 负责），并有守卫钉住它不出现。
   ⚠️ **`script-src` 里仍有 `'unsafe-inline'`，所以它现在还挡不住内联脚本注入** —— 去掉它需要先解决
   三处内联：主题初始化脚本、每页内容不同的 JSON-LD（⇒ hash 方案要在渲染时算 hash 再塞进响应头，
   caddy 做不到）、以及站长自己写的 `customScript`。**在 `report` 模式 + `unsafe-inline` 下，
   这一层的价值是"把违规暴露出来"和挡住 `object`/`base`/表单外发/被框，不是 XSS 的第二道防线**，
   别高估它。想自己写整条策略用 `VANBLOG_CSP_OVERRIDE`（⚠️ 故意不提供"往任意指令追加"的入口，
   那等于允许把 `script-src` 悄悄放宽成 `*`）；只想加来源用 `VANBLOG_CSP_EXTRA_SCRIPT_SRC` /
   `_EXTRA_CONNECT_SRC`；违规报告地址用 `VANBLOG_CSP_REPORT_URI`（⚠️ **建议指向你自己的日志服务**：
   这个端点匿名可写，接在本站上就是现成的日志炸弹/DoS 面）。
- **未捕获异常现在会让进程以非 0 退出**（FATAL 日志 + 跑关停钩子，3 秒硬上限，然后 `exit(1)`），
  交给容器的 `restart` 策略处理。以前只记日志继续跑，于是会出现"容器 `Up`、健康检查 200、
  `restart: always` 永不介入，而进程已经处于未定义状态"—— 这正是 `scripts/start.js` 当初重写要修的
  故障形状，而本轮真的找到了一个会产生这类异常的地方（备份的 NDJSON 写流没有 `error` 监听）。
  ⚠️ `docker stop` / `compose down` 走的是 SIGTERM 路径，**仍然退出 0**，不会被当成失败。
  `unhandledRejection` 仍然只记日志：本仓库有大量 fire-and-forget 的写库，一律退进程会误杀。
- **流水线依赖名收口**：不接受以 `/` 开头的绝对路径、含 `..` 的路径段、以及 `file:` / `link:` /
  `workspace:` 三种协议（以前字符集里含 `/ . ~ ^`，所以 `../../../x` 能通过并从容器内任意路径安装）。
  `user/repo`（GitHub 简写）与 `./local-dep`（runner 目录内的相对路径）**仍然允许** ——
  能写流水线的人本来就能执行任意代码，禁掉这两种只会弄坏正常用法而不增加安全性。
- **自定义页面的 302 只允许同源相对路径**：协议相对的 `//host/x`、`/\host`、以及含 CRLF 的形状一律
  **404**（与该 controller 其它分支同样的措辞，且**不回显**输入）。
  ⚠️ 澄清一个此前的误判：这个跳转目标**不是**管理员可写的数据库字段，而是从 `req.url` 推导出来的
  `${pathname}/${search}`，唯一用途是补一个尾斜杠，所以正常值永远长这样：`/c/xxx/`。
  也就是说没有站点存着"外链跳转"数据会被这次收口弄坏 —— 这也是为什么选择直接 404，
  而不是加一个"你要离开本站"的中间页（那会多一个活动部件却什么也没保护到）。
- **正文 HTML 白名单收紧**（详见 [编辑器与正文](../features/editor.md#正文里可以写哪些-html)）：
  `data:` 只对 `<img src>` 放行；`<iframe src>` 只接受 `http(s)://` 与协议相对的 `//`；
  内联 `style` 只给排版类标签（**`<a>` / `<input>` / `<button>` 上的 style 会被摘掉**）；
  正文里的 `<style>` 块整段删除（含内容）。
  ⚠️ **如实写明局限**：`div` / `span` / `p` 仍然可以带 `style`，所以
  `<div style="position:fixed;inset:0;z-index:9999">` 这种**全屏遮罩**依然做得出来
  （可用于点击劫持式的诱导）。要堵住它需要**值级**的 CSS 过滤（真正的声明解析器，不是正则 ——
  正则会把 `content:"a;b"` 误判），代价是会误伤正常的粘性侧栏与高层级弹层。本轮没有实现，属站长取舍。

## jwt 密钥轮换

站点的 jwt 签名密钥存在数据库的 `settings` 集合里（`type: 'jwt'`），而**整站归档会把整个数据库打包带走** —— 所以一份泄露的归档里就有这把密钥，拿到它的人可以**自签一个管理员令牌**，不需要破解任何口令。怀疑归档泄露时，正确的动作是轮换密钥：

```
POST /api/admin/backup/jwt/rotate        # 要管理员登录态（token 头）
```

⚠️ 这条路由在**超管专属前缀**下 ⇒ 勾了「所有权限」的协作者**调不到**（见 [协作者](./collaborator.md)）。响应里带 `restartRequired`（要不要重启才生效）与 `apiTokensAffected`（有多少个 API Token 会受影响）。

轮换之后会发生什么，四句话：

1. **宽限期内旧会话不掉线**。验签先看 token 头里的 `kid`（密钥标识，取密钥 sha256 的前 16 位十六进制 —— 它是密钥的纯函数，所以老库、老归档里没有这个字段也算得出来，**不需要数据迁移**），在当前密钥与宽限期内的上一个密钥之间二选一。宽限期由 `VANBLOG_JWT_ROTATE_GRACE_DAYS` 决定，默认 **7 天**。
2. **宽限期满之后，所有旧登录会话与全部 API Token 一起失效**。外部集成（自己写的发布脚本、IFTTT 之类）要到后台**重新签发** Token。想立刻断开就把宽限期设成 `0`（慎用）。
3. ⚠️ **恢复一份旧归档会把密钥回滚**：`settings` 在归档里，恢复时连同 `previous` 与 `rotatedAt` 一起被归档里那份覆盖 ⇒ 密钥回到归档导出时的值。**如果你正是因为怀疑泄露才轮换的，那么恢复旧归档等于把泄露过的密钥装回来** —— 恢复完请再轮换一次。
4. ⚠️ **评论者的会话也会受影响**：内嵌 waline 子进程的会话密钥是**从本站 jwt 密钥派生**的，所以轮换之后**下次重启 waline** 会让所有评论者的登录态失效（要重新登录才能评论）。这不是 bug，是"一把密钥派生全站"的必然结果；不想影响评论者就把轮换安排在低峰期。

::: tip 什么时候该轮换

- 怀疑整站归档泄露（备份盘被读走、对象存储桶配错权限、归档当附件发出去过）；
- 交出去过 `VANBLOG_ADMIN_TOKEN`（`install-cron` 会把它写进 0600 的 env 文件），或怀疑后台令牌被 XSS 读走；
- 从一份**来路不明**的归档恢复过站点（那份归档里的密钥是别人生成的）。

轮换本身很便宜（不重建数据、不停服），贵的是第 2 条：宽限期满后所有 Token 都要重签。所以**轮换之后请顺手记一下日期**，在宽限期结束前把外部集成的 Token 换好。

:::

## 2026-09 抗攻击这一轮的加固清单

这一批的目标不是"修某个漏洞"，而是**在敌意网络下不被打瘫**：把每个匿名可达的接口从"一个廉价请求换服务端一大笔工作"改成"换不到"。每条都写了**谁能触发**与**代价**。

### 请求体与净化：匿名请求烧不到 CPU 了

- **匿名请求拿不到大 body 限额**（`utils/bodyLimit.ts`）：`/api/admin/article`、`/api/admin/draft`、`/api/admin/customPage`、`/api/admin/pipeline` 这四个前缀需要 50MB 的 JSON 限额（正文可以内嵌 base64 图片、整页 HTML/JS）。⚠️ 但**解析与净化都跑在限流器与鉴权之前**，所以匿名攻击者朝 `/api/admin/article` 投一个 50MB 的 JSON，服务端会先花约 **2.9 秒解析 + 4.6 秒净化**，然后才回 401；被限流挡成 429 的请求**同样已经把 CPU 烧完了**。现在：请求没带 `token` 头时，这四个前缀先按 **1mb** 解析，超了直接 **413**。⚠️ 顺序是关键 —— 这道挡板必须挂在大限额解析器**之前**，挂反了等于没有。⚠️ 它只是粗判（伪造一个 `token` 头仍能拿到大限额、烧掉解析成本，然后在鉴权层被拒），所以**必须与下面那条一起做**，任何一条单独都不够。
- **净化有成本上界**（`utils/sanitizeRequest.ts`）：递归净化 `$` 前缀键与原型污染键时，最多访问 `VANBLOG_SANITIZE_MAX_NODES`（默认 **50000**）个 JSON 节点，超了**拒绝请求（413）而不是跳过净化** —— 跳过就等于把 `$` 操作符与 `__proto__` 原样放过去，"太大"不能变成绕过净化的条件。效果是把最坏情况从"50MB ≈ **7.5 秒同步阻塞事件循环**"压到约 **33 毫秒**。⚠️ 在那之前，默认单 worker 下约 **8 个这种请求/分钟**就能让事件循环 100% 忙，于是前台 SSR 与健康检查全部假死，而容器仍然显示 Up、`restart` 策略不介入。⚠️ `0` **不是**关闭（它是安全边界，没有关闭档位，写 `0` 会被夹到 1000）。
  为什么 50000 够用：本站的大 body 大在**字符串值**上，而净化只递归对象与数组、字符串原样返回 ⇒ 50MB 的合法正文只花几十个节点；200MB 的 JSON 导入走 multipart，根本不经过 `express.json`。

### 读放大：出口带宽是最先耗尽的资源

- **匿名的"含全文列表"单页夹到 20 条**（`controller/public/public.controller.ts` 的 `FULL_CONTENT_MAX_PAGE_SIZE`）：文章列表默认（`toListView` 缺省 = false）会在每一项里带**完整正文**，于是一个约 60 字节的匿名请求能换回约等于整库正文的响应体（本站 59 篇 / 41,508 字，`pageSize=100` 一次就是整库）。⚠️ 在极端环境下**出口带宽是最先耗尽、且最难恢复的资源**，而按 IP 限流对僵尸网络无效。谁不受影响：①**前台**（列表页一律显式传 `toListView=true`）；②**本站内部调用**（SSR 带 `VAN_BLOG_INTERNAL_TOKEN` 或回环直连）；③第三方消费者仍然可用，只是拉全文要分 5 倍多的页。
- **公开只读接口带缓存头**：`GET /api/public/meta` 与 `GET /api/public/article` 下发 `Cache-Control: public, max-age=30, s-maxage=300, stale-while-revalidate=86400`。意义是**站长只要在前面挂任意 CDN 或带缓存的反代，就能把这类流量吸收在边缘** —— 这是极端环境下唯一能横向扩展的防线。⚠️ **文章详情与解锁接口故意不给**：含访问密码保护的内容绝不能被共享缓存存住。
- **meta 接口的并发合并（single-flight）**（`utils/publicMetaCache.ts`）：这是全站最热的一次读（前台每个页面渲染都要调），有 5 秒进程内缓存。⚠️ 但**光有 TTL 缓存不够**：TTL 到期的那一瞬间，一万个并发未命中会各自跑一遍 7 个查询的 `Promise.all`，一起压向 100 条连接的 Mongo 池 —— 这是个**周期性必然发生**的故障形状。现在同一时刻只有一次底层取数，其余请求等同一个 Promise。设 `VANBLOG_PUBLIC_META_CACHE_MS=0` 可以关掉（关掉时并发合并也一并失效）。

### 登录与凭据

- **两层防爆破**：按 IP 的 5 次/300 秒照旧；**新增全局失败速率节流** —— 全局每分钟失败超过 `VANBLOG_LOGIN_GLOBAL_FAIL_PER_MIN`（默认 120）之后，给**所有**登录请求加延迟（每超一倍 +500ms，封顶 `VANBLOG_LOGIN_THROTTLE_MAX_MS`，默认 3 秒）。⚠️ **这是加延迟，不是封号**：密码正确的人照样登得进来，只是慢。
  ⚠️ **代价要如实说**：被大规模撞库期间，**站长自己登录也会慢最多 3 秒**。这是有意的取舍（慢 3 秒 vs 登不进来）。之所以**不做**"按用户名锁定"：那会让攻击者把真管理员永久锁在门外、而且可以无限续期 —— 在"要持续对外发布"的场景下，那比撞库本身更致命。
  为什么需要全局这一层：按 IP 的计数在僵尸网络/大量代理 IP 下等于没有，而每次登录尝试都要跑一次 scrypt（实测 63–65ms / 16MB 内存）。
- **登录失败计数从"无界进程内对象"搬到有界表**（`utils/attemptLimit.ts`）：旧实现给每个来源 IP 建一条记录且没有上限，**换源 IP 猛打登录就能把内存撑爆**。现在是 20000 个桶的硬上限 + 满表时按 count 淘汰最冷的（洪水桶 count=1 先走，正在被限流的热桶一条不动）；顺带的好处是**成功登录不再写入任何东西**（旧实现会给每个成功登录的 IP 写一条 `{count:0}`）。
- **scrypt 改成异步**（`utils/crypto.ts`）：口令哈希的 CPU 与内存开销落到 libuv 线程池，**不再冻结事件循环**。⚠️ 注意这不减少 CPU 总量 —— 线程池被打满之后，图片管线等其它异步工作会一起排队，所以上面那些"减少尝试次数"的闸门仍然是必要的。
- **口令最小长度**：账号（管理员/协作者）**≥10** 个字符；分类的访问密码是**另一套策略**（≥4，4~7 个字符允许保存但打 WARN，且它**不经** sha256 派生，服务端直接强制）。
  成立的**范围**是：后台四个「设置口令」的入口（初始化向导、协作者新建/修改、忘记密码重设、改管理员口令）**加**零接触初始化的 `VANBLOG_ADMIN_PASSWORD` / `VANBLOG_ADMIN_PASSWORD_FILE`（那是原始口令，不达标**直接拒绝启动**并给出可照做的提示）。
  ⚠️ **三处不成立，别误读**：①**登录表单故意不加**下限 —— 强度校验属于「设置口令」的时刻，不属于「证明口令」的时刻；加了会把历史短口令账号**永久锁在门外**（只能走「忘记密码」+ 恢复密钥，而恢复密钥每次重启都会变），这个决定有守卫钉着；②直接调 API 且传**原始**口令的客户端（脚本、curl、第三方集成）由服务端 `assertAccountPasswordStrength` 负责；③访问密码走的是上面那套独立策略。
  ⚠️ **为什么表单才是强制点**：后台所有涉及账号口令的入口都在浏览器里先做 sha256 派生再发出来，派生结果**恒为 64 个十六进制字符**、与原始口令长度无关且不可逆 ⇒ 服务端在后台路径上**数学上就判不了**原始强度。
  ⚠️ **存量账号不追溯**：只在下次设置口令时生效，既有的弱口令账号不会被锁死。
  为什么是 10：本轮把协作者权限**从「从来没生效过」修成了真的生效**，在那之前一个 1 字符口令的协作者账号其实什么也做不了；修好之后同样的弱口令几分钟就能被撞开，而撞开之后能改内容。
  为什么是 10：本轮把协作者权限**从"从来没生效过"修成了真的生效**，在那之前一个 1 字符口令的协作者账号其实什么也做不了；修好之后同样的弱口令几分钟就能被撞开，而撞开之后能改内容。
- **网段白名单**（`VANBLOG_ADMIN_LOGIN_ALLOW_CIDR`）：只允许指定网段**登录后台**。⚠️ **配错 = 全部拒绝**（fail-closed，不会"配错就放行"），所以第一次配完请**另开一个隐身窗口确认自己还能登录**再关掉当前会话。被拒时返回 403，文案**故意含糊**（不告诉探测者"这里配了网络限制"），真实原因在服务端日志里。三条边界：①**只管登录**，已签发的会话与 API Token 不受限；②「忘记密码」恢复接口**故意不纳入**（那是站长在 VPN 之外唯一的自救入口）；③强度取决于转发头是否可信 —— 如果 `VANBLOG_TRUST_FORWARDED_HEADERS=always` 而站点直接暴露，攻击者能伪造白名单内的 IP，这种情况请把 `VANBLOG_BRUTE_FORCE_IP_SOURCE` 设成 `socket`。
- **API Token 默认有效期 365 天 → 90 天**：Token 等价于超级管理员（签的就是 `id: 0`），有效期就是"泄露之后攻击者能用的时长"上限。已签发的不受影响。

### 内存与磁盘：不给"无界增长"留口子

- **`CacheProvider` 有 64 个键的硬上限**（`provider/cache/cache.provider.ts`）：超出就**拒绝写入并打 ERROR**（同一个键只打一次，避免刷日志）。⚠️ 为什么是"拒绝"而不是"淘汰最旧的"：这张表里放的是**凭据**（恢复密钥），淘汰掉一个凭据等于让一次合法的恢复失败。
  ⚠️ **给开发者的规矩**：任何"按外部输入分桶"的计数或缓存都**不许**放 `CacheProvider`（攻击者能造出无限多个键），请用 `utils/attemptLimit.ts`（有 20000 桶上限与淘汰策略）。本轮之前就有一个按 IP 分桶的登录计数放在这里，换源 IP 就能让堆单调增长。
- **上传前检查磁盘余量**（`utils/uploadLimits.ts`）：剩余空间不足 `VANBLOG_UPLOAD_MIN_FREE_BYTES`（默认 500MB）就拒绝上传并说明差多少。⚠️ 读不到剩余空间时**跳过**闸门而不是拒绝（没有 `statfsSync` 的平台不该因此让所有上传全部失败）。
- **图片扫描的三个成本上限**：篇数（`VANBLOG_IMG_SCAN_MAX_ARTICLES`，默认 5000）、链接数（`VANBLOG_IMG_SCAN_MAX_LINKS`，默认 2000）、并发（`VANBLOG_IMG_SCAN_CONCURRENCY`，默认 4，以前是串行）。⚠️ 撞上限时**如实报告没扫完**（响应里带 `truncatedArticles` / `truncatedLinks`，日志有 WARN）—— 静默返回不完整结果会让"补缩略图/找失效图"这类维护动作得出错误结论。单个链接失败也不再让整轮失败。
- **隐写检测的上传字节另有 8MP 上限**（`MAX_STEGO_DETECT_PIXELS`）：检测要把整图解码成 raw RGBA 再逐像素比对，实测 36MP → 401ms、RSS 477MB ⇒ 3 个并发就约 1.4GB，常见的 1–2GB 容器直接 OOMKilled；而这条路由在免权限档 `publicRoutes` 里（**协作者勾了任意一项权限**即可调，是有意为之：图片管理页要给协作者用），全局桶 600/分钟对它太宽（= 每分钟 240 秒 CPU）。⚠️ 8MP 只作用于**上传来的字节**；按 sign 检测走的是图床里已存在的文件（上传时已经付过代价），那条路**不套 8MP**，否则"验一张自己库里的 20MP 图"会莫名失败。真要验更大的图，先上传到图床再按 sign 检测。

### 远程 DoS：两处二次复杂度

- **正文图片链接解析从二次改成线性**（`utils/parseImgOfMarkdown.ts`）：旧实现用一条正则做全局扫描，`([^\s)>]+)` 在遇到"没有终止符"的输入时会一路吃到字符串末尾再逐字符回溯，而全局扫描会在**每一个** `![` 起点重来一遍 ⇒ O(n²)。实测（跑仓库真函数）：用 `![a](http://` 重复填充，20,000 字节 → 209.9ms，200,000 字节 → **20,899ms**（10 倍输入 → 100 倍时间），拟合下去 **1MB 恶意正文约 572 秒、2MB 约 38 分钟**；同尺寸的正常 markdown 只要 24.6ms。吃这个函数的是**请求体里的正文**（保存文章、`covers/from-content`、`transfer-remote`），所以那是一条同步阻塞事件循环的远程 DoS。现在改成手写线性扫描器，语义与旧正则**逐字符等价**（有差分 fuzz 守卫：随机输入下与旧正则输出逐项相同），并另有一道工作量预算兜底。
- **`/page/[p]` 的参数形状校验放在取数之前**（`packages/website/pages/page/[p].tsx`）：这个页面是 `fallback: "blocking"`，任何没在构建期生成过的路径都会在第一次被访问时现场跑一遍完整 SSR（读 meta/settings/文章列表）并往 Next 的文件系统缓存写一条，而 **Next 14 的 fs cache 没有淘汰上限** ⇒ 攻击者不停请求互不相同的随机 URL，就能同时打 CPU、Mongo 和磁盘，而且**按 IP 限流挡不住**（每个 URL 只打一次）。现在是纯字符串判定（不打 server、不查库、不做 SSR），除历史上的 `/page/abc`、`/page/0`、`/page/-3` 之外，还挡住超长入参、控制字符（含换行 ⇒ 日志与响应头注入的原料）、路径分隔符与 `..`（`%2F` 解码后就是 `/`）、以及超过 `Number.MAX_SAFE_INTEGER` 的页码。

### 不再主动向外发请求

- **版本检查默认关闭**（`utils/getVersion.ts`）：旧默认值指向上游作者的版本服务，而调用点在 `meta.controller` 的**构造函数**里（依赖注入期间就执行）⇒ **每次启动**、以及缓存过期后每次打开后台，都会向一个与本部署无关的域名发请求，带出去的是本站**出口 IP** 和"这里在运营一个 VanBlog"这个事实。在极端环境下这两条都能被用来关联与定位运营者。现在**默认一个字节都不发**（DNS 都不查）；`off`/`false`/`none`/`disabled`/`0` 都当关闭处理。想知道有没有新版本请看仓库的 Releases 页面（后台「关于」页有链接）—— 上游返回的 `0.54.0` 与本项目的 `v2026.x@sha` 形状本来就不可比，只会产生假警报。

### 有意没有改的一处（别当成疏漏去优化）

`/post/[id]` 的 `fallback: "blocking"` 是**有意保留**的。会有人拿"随机不存在的 slug 会触发按需 SSR，是最便宜的放大攻击"当理由想改成 `false`，但那个理由的两个前提都不成立，而代价是**可用性回归**：

1. `getStaticPaths` 只列**规范地址**（有别名用别名、否则用数字 id），而服务端把 `/post/<数字id>` 与 `/post/<别名>` **两条**都当公开地址去 revalidate ⇒ 有自定义别名的文章，它的数字 id 地址**不在**构建清单里，只有 blocking 能按需生成那条 301。改成 `false`，老链接、收藏夹、搜索引擎收录里的数字 id 地址**全部变成硬 404**。
2. blocking 是**自愈**路径：容器重建后 `.next` 里只有构建期那些页面、ISR 缓存是冷的，或者某一次 revalidate 触发丢了（前台正在重启、那轮风暴被合并掉）—— 这两种情况下访客的一次请求就能把页面重新生成出来；`false` 只能等下一次 revalidate 或整点兜底 cron。

而它"防住"的开销其实很小：假 slug 走的 `getPublicMeta()` 有 5 秒缓存 + 并发合并（洪水下约等于免费）；文章查询是**索引精确匹配**；服务端查不到时**立刻抛 404**，相关文章/前后篇/加密分类名单那些重活根本不执行 ⇒ 每个不同的假 slug ≈ 一次索引查询 + 一次 404 渲染。⚠️ 真要拦这个放大，落点是**边缘层**（CDN 或 caddy 对未命中的 `/post/*` 做短 TTL 负缓存或限流），不是把 fallback 改成 `false`。

## 已知限制（尚未处理）

- **全站 CSP 已有，但默认是 `report`（只报告不拦截），而且 `script-src` 里还有 `'unsafe-inline'`**
  （2026-09-20 起，见上面「CSP」那条与 `VANBLOG_CSP_MODE`）。⚠️ 旧版这里写的是「没有 CSP」，已作废。
  真正剩下的限制是：去掉 `'unsafe-inline'` 需要先给三处内联脚本发 nonce 或改外链 —— 主题初始化脚本、
  **每页内容都不同**的 JSON-LD（hash 方案要在渲染时算 hash 再写进响应头，caddy 层做不到）、
  以及站长自己在「定制化」里写的 `customScript`。⚠️ 另有一条已知无解的取舍：**ISR 缓存的页面里 nonce 会被复用**，
  而同源攻击者本来就读得到那份 HTML ⇒ **前台不该用 nonce**，只能用 hash 或来源白名单；后台（非缓存）才适合 nonce。
- **没有全局 `ValidationPipe`**（`class-validator` 不是依赖），参数校验靠各处手写；
  请求净化中间件是「黑名单」而不是「白名单」。

## 容器以 root 运行：这意味着什么，以及本轮做了什么

这一节是**如实的风险说明**，不是"已加固完毕"的宣告。站长的裁定是：本轮**不改镜像**、不做 su-exec/setcap 降权，
只在编排层尽量收窄，并把代价写清楚。所以下面每一条都区分了"已做"与"没做、为什么"。

### 事实：谁能拿到容器内的 root

- 容器**以 root 运行**（caddy 要绑 80/443，数据目录是宿主 bind mount）。
- **流水线功能在设计上就是代码执行**：它把管理员写的代码写进 `/app/codeRunner` 再 `fork()` 执行。
  所以"一个管理员会话被拿下 = 容器内 root"不是漏洞，是产品功能的结果。
- 流水线**只有超级管理员能碰**：`/api/admin/pipeline` 在超管专属路由表里
  （`packages/server/src/types/access/access.ts`），所以勾了「所有权限」的协作者**碰不到**它。
- ⇒ 能拿到容器内 root 的是三种主体：**管理员本人**、**被盗的管理员会话**、以及**管理员签发的 API Token**。
  ⚠️ API Token 等价于超管（`{sub:0, role:'admin'}`），默认有效期已从 365 天降到 **90 天**。

### 拿到容器内 root 意味着什么

不夸大也不淡化，按"能读到什么、能改什么"来说：

| 能力 | 具体内容 |
| --- | --- |
| 读**所有挂载卷** | 静态文件（图床原图）、日志、**整站备份归档**、caddy 的配置与**证书私钥**、mongo 数据目录 |
| 读归档里的凭据 | 归档含**全部口令哈希**与 **jwt 签名密钥**（`utils/fullBackup.ts` 的注释原文：拿到 jwt 密钥就能**伪造管理员 token，不需要破解任何口令**）。归档现在还可能含 **caddy 的 TLS 材料**，所以归档能放在哪的要求被抬高了 |
| 改数据库 | mongo 数据目录是可写的 bind mount ⇒ 可以直接改库（绕过应用层的一切校验） |
| 改 caddy 配置 | 可以改反代规则、改证书来源 ⇒ 可以把流量导走 |
| 在容器内驻留 | 可以留后门进程/文件；`restart: always` 会把它一起带回来（除非重建容器） |

⚠️ **边界（这条必须说清，不要当成安慰）**：能不能从容器**逃到宿主机**，取决于容器运行时与内核的版本与配置。
**本轮没有做任何逃逸测试**，所以这里既不声称"逃不出去"，也不声称"能逃出去"。
上面这张表说的是"容器内 + 挂载卷"这个范围内的确定事实；bind mount 意味着**容器对这些宿主目录的权限就是宿主权限**
（这一条在 [备份与恢复](backup.md) 里已经写过，此处只引用不重复）。

### 本轮在部署层做了什么

compose 模板（`docker-compose/docker-compose-template.yml`）：

- ✅ **启用** `security_opt: [no-new-privileges:true]`（只对 vanblog 服务）。
  它挡的是"**在已经是 root 之上**再提权"的路径（setuid 二进制、文件 capability），
  ⚠️ **不是**"防止拿到 root"。已核实对本项目安全：`entrypoint.sh`、`scripts/start.js`、`Dockerfile` 里
  `gosu`/`su`/`setpriv`/`setuid`/`newgrp` 零命中，`chown`/`chmod` 也是 0 处 ⇒ 没有依赖提权的启动步骤。
  有守卫钉住这个前提：将来有人往 entrypoint 里加 `gosu` 之类，守卫会红（因为那时这一行会让启动失败，
  而失败形状是"容器起不来"、很难联想到这里）。
- ⚠️ **mongo 服务故意不加**：官方 mongo 镜像的 entrypoint 以 root 启动时会自己降权到 mongodb 用户，
  那条路径依赖 setuid/setgid 语义；本轮没有容器可实测，所以不动它。
- ❌ **`read_only: true` 不可行**，四个阻塞点都已核实（不是推测）：
  ① `entrypoint.sh` 每次启动都要写 `/app/caddy.json` 与 `/app/caddy-fallback.json`（在**镜像层**里，不是卷）；
  ② 流水线要写 `/app/codeRunner` 与 `/app/pluginRunner`（不是卷）；
  ③ **ISR 产物**写在 `/app/website/packages/website/.next/server/pages/**`（不是卷；实测过：渲染一篇真文章后
  它的 `.html`/`.json`/`.meta` 会出现在那里）⇒ 只读根会让**页面缓存完全写不了**；
  ④ `/tmp` 用于上传与整站恢复解包的临时文件。
  要做只读根，前提是先把 ②③ 变成卷、把 ① 的输出改到可写路径 —— 那要改 entrypoint，属"改镜像"，本轮裁定不动。
- ❌ **`cap_drop: [ALL]` 默认不启用**，因为风险是真实的且本轮无容器可实测：容器以 root 写**宿主属主**的
  bind mount，靠的是 `CAP_DAC_OVERRIDE`；只加回 `NET_BIND_SERVICE` 的话，宿主目录属主不是 root 时就会
  **写不进去**（图片上传失败、日志写不出、备份失败），而且是"容器 Up、功能坏"的难查形状。
  要打开就至少 `[NET_BIND_SERVICE, DAC_OVERRIDE, CHOWN, FOWNER]`，并自己把上传/备份/恢复/HTTPS 签发跑一遍。
- ❌ **`pids_limit` 默认不写**（防 fork 炸弹这一条确实值得做，流水线能 `fork()`）。不写的原因是**版本兼容**：
  已实证 docker-compose **1.29.2** 的 schema（`compose/config/compose_spec.json`，`additionalProperties:false`）
  里有这个键；但 **1.25** 用的是按版本分的 3.4 schema，那份文件本轮没取到，而 v2-only 的键在 3.x 下会被直接拒绝
  （本模板开头选 `version: '3.4'` 的注释记的就是同一类事故）。⇒ 只在确认自己是 compose v2、或
  docker-compose ≥1.27（1.27 起忽略 `version` 字段、改用统一 spec）时才打开，值从 **512** 起步。
  ⚠️ 同一类版本陷阱也适用于模板里另一处建议的 `mem_limit`（**这是既有的、不是本轮引入的**）：
  打开前先 `docker-compose config` 验一遍，别直接 `up`。

这三项"故意不启用"都被守卫钉住了（`scripts/tests/vanblog-compose-health.test.sh`）：**剥注释后必须不存在**，
同时**注释里必须有**（带理由与打开方法）。所以想打开它们的人会先撞红、读到理由，而不是"顺手加上、站点起不来"。

k8s 清单（[Kubernetes 部署](../guide/kubernetes.snippet.md)）：

- ✅ 补了 `securityContext`：`allowPrivilegeEscalation: false`（= no-new-privileges，与 compose 同口径）、
  `seccompProfile: RuntimeDefault`（k8s ≥1.25 本来就是默认值，显式写出来是为了"集群默认策略变了也不会静默放宽"）、
  以及**如实**的 `runAsNonRoot: false` —— 写出来是为了不误导：PodSecurity 的 `restricted` 档要求
  `runAsNonRoot: true`，所以这份清单**过不了 restricted**，只能用在 `baseline` 或无策略的命名空间。
- ❌ `capabilities` 收窄**没有默认打开**，理由与 compose 的 `cap_drop` 完全相同（root 写宿主属主 hostPath
  靠 `CAP_DAC_OVERRIDE`），清单里给了带这四个 cap 的注释版可选写法。
- 🔴 **顺带修了一个真缺陷**：清单里的 `limits:` 原来缩进成**容器的同级键**（与 `resources:` 平级），
  而它不是合法的 Kubernetes 字段 ⇒ `kubectl apply` 会被严格校验拒绝；若加了 `--validate=false` 就被静默丢弃，
  **内存与 CPU 上限等于完全没设**。PyYAML 能解析它（它是合法 YAML），所以只有解析后按 k8s 语义检查才发现得了 ——
  现在守卫就是这么验的。
- ⚠️ 同时把内存上限从 **500Mi 抬到 1536Mi**：整站备份用 `zstd -19 --long=27 -T0`（多线程 + 128MB 窗口），
  峰值能到 **1GB 上下**；实测这套站点在并发压测下 RSS 是 568MB～1.1GB。**500Mi 会把备份 OOM 杀掉**。
  节点内存真的紧张时，正确做法是**降低压缩等级**（`VANBLOG_BACKUP_ZSTD_LEVEL: '12'`）而不是压低上限。

### 为什么不做 su-exec / setcap 降权

这是站长的裁定，代价也如实记下（属另一轮的工作量，不是"忘了做"）：

1. **挂载卷属主**：现有部署的数据目录属主是宿主机上创建它的那个用户；降到非 root 后要么改属主（会影响宿主机上
   的其它访问），要么靠 `userns`/`fsGroup`，两种都需要迁移步骤与回滚方案。
2. **caddy 绑 80/443**：非 root 需要 `NET_BIND_SERVICE` 文件 capability（`setcap` 打在镜像里的二进制上）
   或改成高位端口 + 宿主转发，两者都改变现有部署的网络口径。
3. **流水线子进程的权限继承**：`fork()` 出来的 node 子进程会继承降权后的身份，而 `pnpm add` 要写
   `/app/pluginRunner` ⇒ 降权后这些目录必须可写，等于把"哪些路径必须可写"这件事全部重新梳理一遍
   （与上面 `read_only` 的四个阻塞点是同一份清单）。

### 站长现在就能做的缓解（按性价比排序）

| # | 做法 | 说明与注意 |
| --- | --- | --- |
| 1 | **把后台限制在可信网段** | `VANBLOG_ADMIN_LOGIN_ALLOW_CIDR`（默认关）。⚠️ 它**只限登录**：已经签发的 token 与 API Token **不受限**，所以配合第 2 条一起用 |
| 2 | **API Token 用完即吊销、有效期别拉满** | Token 等价超管 ⇒ 泄露一个 Token 就等于泄露后台。默认 TTL 已是 90 天，能更短就更短 |
| 3 | **备份归档必须加密，或至少离线签名** | `VANBLOG_BACKUP_PASSPHRASE`（加密）与 ed25519 签名（证明没被篡改）。⚠️ **信任边界**：验签公钥必须存在**主机之外**，否则拿到 root 的人可以连签名一起换掉 —— 签名防的是"归档离开主机之后被篡改"，不防已经有主机 root 的人 |
| 4 | **检查挂载目录在宿主机上的权限** | bind mount ⇒ 容器对这些目录的权限就是宿主权限。归档目录已经是 0700/0600（见 [备份与恢复](backup.md)），但**静态目录与日志目录**通常不是 |
| 5 | **不要把流水线开放给不信任的人** | 它只有超管能碰（协作者勾「所有权限」也碰不到），但请把它当成"给这个人一台容器内的 shell"来授权 |

⚠️ 这一节**不是**在劝你不要用流水线 —— 它是产品功能，很多站长的自动化就靠它。
这里要给的只是"知道代价之后自己决定"所需的信息。


## waline 子树的供应链风险：已裁定「接受现状，只记录」

⚠️ 这一节记录的是一个**已经做出的决定**，不是一条待办。如果你是想找"什么时候修"，答案是：不修，除非下面
「重新评估的触发条件」里的事件发生。

**决定**：waline 评论子树里剩余的依赖漏洞（本轮审计口径：**4 个 critical + 14 个 high**）**接受现状**，
不升级、不改架构，只在此记录边界与缓解。

**为什么"升级"不是一个选项**（这条最容易被误解，所以把核实方法写出来）：`@waline/vercel` **没有 3.x**。
在 registry 上核实：该包共 **345 个版本**，`dist-tags` 是 `latest: 1.41.6`、`deta: 1.27.0-deta`、
`netlify: 1.28.0-alpha.3` —— **没有任何 2.x 或 3.x**，而仓库钉的 `1.41.6` 就是树顶（`packages/waline/package.json`
里是精确版本，`pnpm-lock.yaml` 解析为 `1.41.6(@types/node@24.13.5)`）。⇒ "升主版本一次清掉 18 条通告"
这条路**不存在**；本文件与变更日志里以前那句 `@waline/vercel 1→3` 的说法已作废并留了更正痕迹。

**可达性边界**（决定"这个风险有多大"的关键）：这些漏洞**只在启用 waline 评论模式时可达**。
本站的原生评论与 waline 是两条独立的路（waline 是独立子进程、独立的 `waline` 库）；
⚠️ "两者不共享代码"这一点只做过粗核（按依赖与进程边界判断），**没有逐文件复核**，所以别把它当成已证实的结论。

**已经收窄的部分**：根 `package.json` 的 53 条 `pnpm.overrides` 里（其中 35 条带版本作用域），
有 **16 条实际作用在 waline 子树上** —— `axios@0`、`dompurify@2`/`@3`、`path-to-regexp@1`、`ws@5`/`@7`、
`send@0.18.0`、`body-parser@1.20.4`、`braces@3`、`micromatch@4`、`cross-spawn@6`/`@7`、`jws`、`prismjs`、
`form-data`、`browserslist`。⚠️ 这些能生效的前提是**镜像重新构建过**：waline 那棵树以前是孤立 `pnpm i`
安装的（看不到根 manifest ⇒ override 对它无效），本轮已改成走 lockfile（`--frozen-lockfile --filter`）。

**仍未收窄的部分**：🔴 其中 `protobufjs@5.0.3` **没有同主版本的修复**（最新是 8.8.0，跨 3 个主版本）。
它来自 `leancloud-storage@4.15.2`，而本部署用的是 `think-mongo` ⇒ leancloud 实际上是**死重量**，
但它是 `@waline/vercel` 的**直接依赖**，移除属于侵入性改动（要 patch 上游的依赖表），本轮不做。

**将来重新评估时的两个选项**（都没被采纳，理由一并记下）：
1. **继续推进 scoped override**：同主版本内可动的有 `mysql2 3.6.5 → 3.24.4`（纯 JS，性价比最高）、
   `koa@2`、`thinkjs@3`、`jsdom@16`、`undici@5`、`ejs@2`、`semver`、`tough-cookie@2`。
   ⚠️ `tar-fs` 属于**原生编译链**，动它必须用一次真实镜像构建验证 `waline_builder` 阶段还能编出
   `sqlite3` / `better-sqlite3`（这一层在 musl 上没有预编译包，每次都要现场编）。
2. **改用官方 Waline Docker 镜像做独立服务**：一次消灭整棵子树、原生编译层、42 条通告，
   以及下面那条 JWT 密钥耦合；代价是**失去"一个容器搞定"的部署形态**，而且要迁移已有的评论库。

**一条独立的既有耦合（本轮不修，但站长要知道）**：`provider/waline/waline.provider.ts:89` 把
**本站的 jwt 密钥**当 waline 子进程的 `JWT_TOKEN` 传进去（`JWT_TOKEN: global.jwtSecret || makeSalt()`）。
⇒ 用了本轮新增的 **JWT 密钥轮换**之后，waline **下次重启**时评论者的登录会话会失效，需要重新登录才能评论。
（正在运行的 waline 不受影响，因为它已经拿到了旧密钥。）

**一条已知陷阱（现在不用改，将来升 `@waline/client` 3 时会踩）**：
`packages/website/components/WaLine/core.tsx:1` 现在是 `import "@waline/client/dist/waline.css";`，
而 client **3 删掉了 `./dist/*` 这个 exports 通配** ⇒ 升级后会 `ERR_PACKAGE_PATH_NOT_EXPORTED`。
改成 `@waline/client/waline.css` 在 **v2 与 v3 都有映射**，是一行零风险的前置改动。

**站长现在能做什么**（按性价比）：
1. **不需要 waline 评论就别启用它**（后台评论设置里选原生评论）。这是唯一能完全消除这块风险的做法。
2. ⚠️ **不要指望"把 waline 端口对内网开放"**：默认的 compose 编排**只发布 80 与 443**（外加 443/udp），
   waline 子进程的 8360 **根本没有映射到宿主机**，它只能经内置 caddy 的同源路由到达
   （`caddyTemplate.json` 里每个 server 有 7 个反代到 `127.0.0.1:8360` 的块）。
   ⇒ 想收窄它的暴露面，只能在 **caddy 的路由层**或**关掉评论模式**，防火墙层面没有独立的口子可关。
3. 如果确实要用 waline：把评论接口纳入你已有的 WAF/CDN 规则（本站的限流是按 IP 的，
   而 `VANBLOG_TRUST_FORWARDED_HEADERS` 必须与你的真实拓扑一致，否则限流会误伤或被绕过）。

**重新评估的触发条件**（满足任一条就该重开这个话题）：`@waline/vercel` 发布了 2.x/3.x；
或 waline 子树里出现了**可匿名触发**的 RCE（现在的 4 个 critical 里，`mysql2` 那两条要能连到它的库、
`protobufjs` 那条要走到 leancloud 路径，都不是匿名评论接口能直接打到的）；
或你决定改用官方镜像做独立服务。

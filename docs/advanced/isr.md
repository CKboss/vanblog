您可以在后台的 `系统设置/高级设置` 中更改静态页面更新策略或者强制触发静态页面更新：

![更新策略设置](https://pic.mereith.com/img/7bb50e93e1ef869b6117cd88c92ebb72.clipboard-2023-02-01.png)

### 静态页面更新策略

有两种：延时自动、按需自动

- 延时自动： 使用 Next.js 内置的静态增量再生，可以设置重新尝试生成静态页面的时间。实时性略低。
- 按需自动： 每当后台有数据更改时，按需触发静态渲染。实时性高，可能需要更多性能。文章会同时刷新数字 ID 地址（`/post/<id>`）和自定义路径地址（`/post/<pathname>`），搜索结果跳到数字 ID 时也能看到最新内容。

### 强制触发静态页面更新

点此按钮可强制触发静态页面的渲染更新，无论设置何种更新策略。

若源站（直连容器端口）已经是新内容，公网反代或 CDN 后面仍是旧文章，请检查外层是否在缓存 HTML，见 [后台发布后前台不刷新仍显示旧文章](../faq/deploy.md#后台发布后前台不刷新仍显示旧文章)（[#469](https://github.com/Mereithhh/vanblog/issues/469)）。

### 几个内建的兜底（2026-09 起）

- **延时秒数有 60 秒下限**：延时自动模式里填的值（前台的 `VAN_BLOG_REVALIDATE_TIME`）低于 60
  会被抬到 60，非法/空值也回落 60。以前的 10 秒意味着有流量时每页每 10 秒重渲染一轮
  （本站一轮 ~130 个路由，每次都要回调 server 的公开接口），而「改完 1 分钟内可见」对个人博客完全够用。
- **按需模式也有 24 小时长保险**：按需生成的页面以前永不过期，全靠 server 的触发；
  万一某次触发丢了（前台容器正在重启、网络抖动），页面会一直停在旧内容上。现在按需模式
  也带 24 小时的 revalidate，最坏从「永久陈旧」变成「最多陈旧一天」。
- **失效产物清理器**：主进程默认每 15 分钟对账一次（`VANBLOG_ISR_REAP_INTERVAL_MS`），
  删掉「库里已不可见但磁盘上还留着」的静态 HTML —— 删除、隐藏、加密、未到点的定时文章都算。
  这也是 caddy 直发 HTML（`VANBLOG_CADDY_SERVE_HTML`，默认关；`all` 模式覆盖文章页等动态路由，
  要求 ISR 是按需模式）敢于存在的前提：直发是按文件发的，磁盘上留着什么就发什么。
  清理器与该开关**解耦**，直发关着也照跑。实测数字见 [性能实测](./benchmark.md)。
- **静态搜索索引跟着同一条触发链走**：每次全量渲染（保存文章、手动触发、每小时兜底 cron）
  会顺带重建 `/static/search/index.json`，见 [文章搜索](../features/search.md)。
- **全量渲染从"严格串行"改成有界并发**（2026-09 起）：以前一次一个地等每个页面重渲染完，
  59 篇文章没问题，但 1 万篇按每次 200 毫秒算就是 **33 分钟**，这期间新内容出不来静态页；
  而触发点有 30 多处分布在十几个文件里（发文、改分类、改标签、换主题、整站恢复、定时发布…）。
  现在同时在途 `VANBLOG_ISR_STORM_CONCURRENCY`（默认 **4**，可调 1–32）个，并且一轮之内有互斥与
  排队（连着保存 10 篇文章不会叠出 10 轮同时跑的风暴）。⚠️ 没有改成"无界并发"是有意的：
  每一次重渲染都是一次到前台进程的真实渲染（读库 + 生成 HTML + 写盘），并发太高会把前台与磁盘
  一起打满，反而更慢 —— 小机器别调大这个值。
- **单轮规模预算只影响分批，不会少渲染任何页面**：一轮要处理的地址超过
  `VANBLOG_ISR_ROUND_URL_BUDGET`（默认 **5000**）时会**分批**继续做完，并打 WARN 与进度日志。
  ⚠️ 别把它读成"超出的就不渲染了" —— 那等于静默丢内容，而这里只是把"这一轮规模异常大"说清楚。

- **启动时的全量渲染会先等数据库就绪**（2026-09 起）：容器重启后 mongoose 重连往往要几秒到几十秒，
  而改动前的重试窗口只有约 **18 秒**（固定 6 次 × 3 秒），于是「重启 → 数据库还没好 → 6 次探活全失败 →
  `达到最大增量渲染重试次数`」，**这一轮预热被永久放弃**，只能等每小时的定时兜底或访客触发按需渲染。
  在需要持续发布的场景下，这意味着任何能让容器重启的事情（崩溃循环、OOM、`docker restart`）都可能让站点
  长时间停在「没有预热」的状态。现在启动风暴之前会等数据库就绪（`readyState === 1` **且**一次真实 `ping()`
  成功，与健康检查同一口径），上限 `VANBLOG_MONGO_READY_TIMEOUT_MS`（默认 **60 秒**，每秒轮询、每 5 秒一条
  进度日志）。⚠️ **超时不影响启动**：站点照常起来并继续提供已缓存内容，只是打一条 WARN 说清后果与兜底。
  重试本身也改成了**有上限的指数退避**（3 → 6 → 12 → 24 → 30 秒封顶，默认 8 次，纯等待约 **135 秒**，
  三个 `VANBLOG_ISR_RETRY_*` 可调）。
- **探活现在会告诉你该查哪一边**：以前「连不上前台子进程」与「前台有响应但渲染失败（多半是它回源查库失败）」
  都只表现为一次失败，日志里看不出区别。现在两者分开：`连不上前台子进程（ECONNREFUSED）` 与
  `前台有响应但返回 HTTP 500（多半是它回源查库失败，数据库可能还没就绪）`，并带上已等待时间与尝试次数；
  彻底放弃时那条 ERROR 会写清兜底（每小时定时渲染 + 访客触发的按需渲染）与四个可调旋钮。
  ⚠️ 〔2026-09-20 补充〕**401 / 403 有专门的文案**，不再套用「多半是数据库没就绪」那句猜测——
  403 是**鉴权**失败，与数据库无关（见下一节），猜错方向会让人白查半天。

### 重渲染接口怎么鉴权（一体式部署自动生成密钥）

server 触发前台重渲染，走的是前台的 `POST /api/revalidate`。这个接口必须挡住外部调用者
（否则任何人都能反复触发重渲染，是一条现成的放大器），所以它要鉴权。

**一体式镜像（默认）：不需要你配任何东西。** 没设 `VAN_BLOG_REVALIDATE_SECRET` 时，
server 会**自动生成**一把进程内随机密钥（32 字节 / 64 位十六进制），落在
`os.tmpdir()/vanblog-revalidate-secret`（权限 **0600**、原子创建），并通过环境变量下发给前台子进程。
两边因此天然一致，开箱即用。

🔴 **分离部署必须两边显式配同一个 `VAN_BLOG_REVALIDATE_SECRET`**（server 与前台不在同一台机器时）。
自动生成的密钥只在本机文件系统内共享，跨机器传不过去。

::: danger 这里曾经有一个默认配置下必然触发的回归（已修）

这个接口原先有一条「套接字是回环**且**不带转发头就放行」的豁免，注释里还写着
「一体式镜像正是这个形状，所以行为不变」。**那句话是错的**：Next 会给**每一个**请求自动补上
`x-forwarded-for`（`next/dist/server/base-server.js`，用 `??=` 赋值，没有任何开关），
所以「不带转发头」这个条件在 Next 下**恒不成立**。

后果是默认配置下 server→前台的**每一次**重渲染都被 **403** 拒绝：冷启动的全量渲染把重试次数烧光、
打出 `达到最大增量渲染重试次数`，磁盘上**一个文章页产物都没有**。而这又会连带打掉
[降级发布](./degraded-publishing.md)——数据库挂掉时 caddy 要直发磁盘 HTML，
可磁盘上根本没有文章页可发。

⚠️ 它当初没被测试发现，是因为单测的请求替身**总是**带着 `socket.remoteAddress`，
而「运行时拿不到理想形状」那条用例恰恰被写成了「应当拒绝的攻击」。
**替身钉住的是作者的假设，不是现实**——这类盲区在本仓库已经出现过三次。

修法不是把 IP 判定放宽：`??=` 只在缺失时补值、真实反代加的头会保留，看上去可以放宽成「XFF 全是回环就放行」，
但 **nginx 默认并不加 `X-Forwarded-For`**，同机反代部署下 XFF 会被 Next 补成反代自己的回环地址，
于是放大器会被重新打开。所以是给一把真密钥。原来那条豁免的四种保护逐条保留：匿名放大器仍然挡住、分离部署仍然失败关闭、
路径形状校验（`..`、`//`、协议、控制字符、长度）一行未动、「配了密钥就一律要求它」也一行未动。

:::

⚠️ **为什么密钥走文件而不是只写 `process.env`**：cluster 模式下，worker 的环境变量在
`startClusterPrimary()` 时就已经**快照**了，而前台子进程是之后才 spawn 的——那时再写
`process.env`，**已经 fork 出去的 worker 拿不到**，于是每个 worker 各自生成一把密钥，
结果是**非主 worker 触发的重渲染全部 401**。症状是「编辑文章后**部分**请求不刷新」，
非常难查。所以用文件做跨进程通道（谁先创建谁定值，其余读到同一个）。

🔴 排查要点：如果你看到重渲染报 **401/403**，那是**鉴权**问题，不是数据库问题。
按顺序查：①分离部署是否两边配了同一个 `VAN_BLOG_REVALIDATE_SECRET`；
②一体式部署里 server 与前台两个进程是否都拿得到那个密钥文件（只读文件系统会让它拿不到，
此时是**失败关闭**）；③密钥是否被换过（换过就要两边一起重启）。
⚠️ 密钥本身**不会**出现在日志、命令行参数或任何接口响应里。

### 为什么文章页保留 fallback: "blocking"（不要"优化"成 false）

文章页 `/post/[id]` 的 `getStaticPaths` 用的是 `fallback: "blocking"`：没在构建期生成过的地址，
第一次被访问时现场渲染一次并缓存下来。会有人建议改成 `false`（未列出的地址直接 404），理由是
"随机不存在的 slug 会触发按需渲染，是最便宜的放大攻击"。**这个改动不要做**，两个前提都经不起核实，
而代价是可用性回归：

1. `getStaticPaths` 只列**规范地址**（有自定义别名就用别名，否则用数字 id），而 server 侧把
   `/post/<数字id>` 与 `/post/<别名>` **两条**都当公开地址去触发重渲染 ⇒ 有自定义别名的文章，
   它的**数字 id 地址不在构建清单里**，只有 `blocking` 能按需生成那条 301 跳转。改成 `false`，
   老链接、收藏夹、搜索引擎收录里的数字 id 地址会**全部变成硬 404**。
2. `blocking` 是**自愈**路径：容器重建之后 `.next` 里只有构建期那些页面、ISR 缓存是冷的；
   或者某一次重渲染触发丢了（前台正在重启、那一轮风暴被合并掉）。这两种情况下，访客的一次请求
   就能把页面重新生成出来；`false` 只能干等下一次触发或整点兜底 cron。

而它"防住"的开销其实很小：假 slug 走的公开 meta 接口有 5 秒缓存 + 并发合并（洪水下约等于免费）；
文章查询是**索引精确匹配**；server 查不到时**立刻抛 404**，相关文章、前后篇、加密分类名单那些重活
根本不执行 ⇒ 每个不同的假 slug ≈ 一次索引查询 + 一次 404 渲染，不是"全价文章页渲染"。

⚠️ 真要拦这种放大，落点是**边缘层**（CDN 或 caddy 对未命中的 `/post/*` 做短 TTL 负缓存或限流），
不是把 fallback 改成 `false` —— 那是拿真实文章的可达性去换一个很便宜的攻击面。
背景与实测见 [安全](./security.md#有意没有改的一处别当成疏漏去优化)。

顺带一提，**分页页 `/page/[p]` 的做法正好相反**：它在取数**之前**做纯字符串的形状校验，
非法形状（`/page/abc`、`/page/0`、超长入参、控制字符、`..`、超过安全整数范围的页码）直接 404。
区别在于分页地址的合法形状是**可枚举**的（就是正整数），而文章地址的合法形状取决于库里的数据，
所以一个能在边缘就判掉、另一个必须查一次库。

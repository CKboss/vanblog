这一页讲的是**数据库不可达时站点还能做什么**。核心结论：VanBlog 不会因为连不上 MongoDB
就整站下线——它会进入「降级驻留」，继续把**已经渲染好的页面**、**静态资源**和**订阅源**
发出去，等数据库回来再自动恢复，全程不需要重启容器。

::: tip 一句话版本

数据库在**启动期间**就连不上时：进程不退出、容器保持 Up，`/api/public/health` 返回
**503**（而不是连接被拒），首页与已渲染过的文章页由 caddy **直接从磁盘发 HTML**，
图片和附件照常，RSS 与 sitemap 照常；数据库一通，**10–20 秒内**自动完成启动并回到正常模式。

:::

## 为什么需要它

同一场故障发生在不同时刻，后果曾经完全不同：

| 故障时刻 | 以前的行为 | 现在的行为 |
| --- | --- | --- |
| **运行中**数据库被杀 | health 转 503，前台靠 ISR 缓存继续 200，数据库回来后自动恢复 | 同上（本来就不错） |
| **启动期间**数据库不可达 | server 抛错退出 → 容器跟着退出 → **连 caddy 一起死**，图片都发不出去 | 进入**降级驻留**：容器保持 Up，页面/图片/订阅源继续可发 |

第二种情况在生产里是**可达的**：主机重启、`docker restart`、崩溃循环，或者任何能让容器
重启的手段，都会走到「应用与数据库同时冷启动」这条路。而编排文件为了兼容老版本
docker-compose，用的是**列表形式**的 `depends_on`（长格式会让 1.25 上的现有安装直接起不来），
所以并没有「等数据库健康再启动应用」这层门控。

## 默认行为：第一次探到就驻留

`VANBLOG_DEGRADED_HOLD_MODE` 默认是 `immediate`：启动前先探一次数据库，不可达就**立刻**
进入降级驻留，然后在后台按 `VANBLOG_DEGRADED_HOLD_PROBE_MS`（默认 30 秒）继续重试。

⚠️ 这个默认值是一次**有意识的取舍**，请读完再决定要不要改：

- **好处**：以前默认配置下，从「数据库不可达」到「开始发缓存内容」要 **396 秒**
  （实测：第 1 次尝试 127 秒、第 2 次 259 秒、第 3 次 396 秒才放弃），这期间页面全是 **502**。
  现在这个窗口是**秒级**。
- **代价**：一次**短暂**的数据库抖动，也会让站点短暂进入「直发磁盘上最后一次渲染的 HTML」
  模式，期间依赖服务端渲染的功能不可用（见下面的清单）。
- **判断**：在「要持续发布信息」的目标下，**短暂的旧内容远优于六分钟的完全不可用**。

不接受这个取舍就显式设 `VANBLOG_DEGRADED_HOLD_MODE=after-window` 回到旧行为
（先把 `VANBLOG_BOOTSTRAP_DB_RETRY_WINDOW_MS` 整个窗口烧完才驻留）。
⚠️ 打错的值会回落到 `immediate` 而**不是**「关闭」——失败方向是「更快开始发布缓存内容」。

## 降级期间什么能用、什么不能用

**仍然可用**（实测）：

| 路径 | 状态 | 由谁提供 |
| --- | --- | --- |
| `/`、`/post/<已渲染过的别名>`、`/page/*`、`/category/*`、`/tag/*` | **200** | caddy 直发磁盘上的 ISR HTML |
| `/static/*`（图床图片、缩略图、附件、自定义页面资源） | **200** | caddy 的 `file_server` |
| `/rss/*`、`/sitemap.xml`，以及别名 `/feed.xml`、`/feed.json`、`/atom.xml` | **200** | caddy 直发磁盘产物 |
| `/admin` | **200** | caddy 自己的 `file_server`（与降级无关，一直如此） |
| `/api/public/health` | **503** | 占位服务，响应体与正常端点**逐字段同形状** |

**不可用**（实测，别指望它们）：

| 路径 | 状态 | 原因 |
| --- | --- | --- |
| 站内搜索 | **503** | 走 server，需要查库 |
| **未渲染过**的 `/post/<slug>` | **502** | 磁盘上没有对应 HTML，而回源渲染需要数据库 |
| waline 评论 `/ui/` | **502** | 评论要读写数据库 |
| `/robots.txt` | **503** | 由 server **动态生成**（要用库里的 baseUrl），没有落盘产物可直发 |
| 其它 `/api/**` | **503** | 占位服务统一返回 503 与可读原因 |

::: warning 两条必须知道的代价

**一、内容是「磁盘上最后一次渲染的」，可能陈旧。** 降级期间不会有任何新渲染，
所以这段时间里发布的文章改动、新文章、新评论都不会出现在页面上。数据库恢复后
会重新触发渲染，内容才追上。

**二、失效产物的清理器（reaper）在降级期间不跑。** 于是有一个**很窄但不是零**的窗口：
如果某篇文章在数据库挂掉**之前**刚被改成私密或加密，而清理器还没来得及删掉它的
`.html`，那么这篇文章在降级期间**仍然会被公开服务**。要消除它只能等数据库恢复。

:::

::: tip 订阅源不会变陈旧

`/rss/*` 与 `/sitemap/` 在 server 侧**本来就是静态目录服务**（`useStaticAssets`），
不是每个请求现算的——它们的产物由 ISR 渲染流程写盘（`feed.xml`、`atom.xml`、
`feed.json`、`sitemap.xml`，都是临时文件 + 改名的原子写）。

所以降级期间 caddy 直发的，就是**正常模式下 server 会发的同一批字节**，
新鲜度完全相同，只是少了一层 express。⚠️ 不要把它理解成「降级时发的是旧 feed」。

:::

## 怎么判断站点正在降级发布

响应头就是判据，可以直接拿去做监控：

| 响应头 | 出现时机 | 值 |
| --- | --- | --- |
| `X-Vanblog-Static-Html` | caddy 直发磁盘 HTML 时 | 🔴 **固定页（如 `/`）是 `1`，`/post/*` 等动态前缀是 `dynamic`** |
| `X-Vanblog-Static-Feed` | caddy 直发 feed / sitemap 时 | `rss` 或 `sitemap` |

⚠️ **`X-Vanblog-Static-Html` 的两个值不同**，所以「判断这个头是否等于 `1`」的监控规则
对文章页会**误判**。要判断「是否在直发」，请检查这个头**存在与否**，而不是它的具体值。

配合 `/api/public/health` 一起看更准：降级时它是 **503**，响应体形如

```json
{
  "statusCode": 503,
  "data": {
    "status": "degraded",
    "mongo": "down",
    "mongoState": 0,
    "mongoStateText": "disconnected",
    "mongoPingMs": null
  }
}
```

字段与正常时**完全一致**（只是取值不同），所以既有的健康检查解析逻辑不用改。

## 数据库恢复之后

不需要任何人工干预：后台探活发现数据库可达，就关掉占位服务、跑真正的启动流程，
哨兵按降级前的状态**精确还原**（你手动开过的 `VANBLOG_CADDY_SERVE_HTML` 不会被关掉，
本来没开的也不会留下残留）。实测从数据库可达到 health 回到 **200** 约 **10–20 秒**，
而且容器的 `StartedAt` 与重启计数**都没有变化**——是进程内自愈，不是靠编排的重启策略。

::: warning 一个已知的短暂 502

每次「尝试真正启动」期间，占位服务会先让出端口，所以那一小段时间
`/api/public/health` 是 **502 而不是 503**。页面不受影响（哨兵要等启动成功才还原，
所以 caddy 一直在直发磁盘 HTML）。如果你的监控把 502 当作「容器死了」告警，
需要知道这一段是预期的。

:::

## 重启风暴熔断

如果故障持续存在（数据库起不来、配置写坏了），编排层的 `restart: always` 会变成
**无限重拉**：CPU 被打满、日志爆盘，而真正的错误被淹没。所以容器内的 `start.js`
自己做了一层熔断：

- 统计窗口 `VANBLOG_CRASH_WINDOW_MS`（默认 10 分钟）内，**快速崩溃**
  （存活不足 `VANBLOG_FAST_CRASH_MS`，默认 60 秒）累计达到 `VANBLOG_MAX_FAST_CRASHES`
  （默认 5 次）时，**退出前先退避**：从 `VANBLOG_CRASH_BACKOFF_BASE_MS`（默认 5 秒）
  按指数增长，封顶 `VANBLOG_CRASH_BACKOFF_MAX_MS`（默认 5 分钟）。
- 退避期间会打一条 FATAL，明说「熔断只负责降速，请去看上面第一条错误」。
- 一次存活**超过**阈值的运行会把计数**清零**，否则一次历史故障会永久拖慢之后的偶发崩溃。
- 计数存在 `VAN_BLOG_CRASH_STATE_FILE`（默认在**挂载的日志目录**里），所以跨容器重建仍然有效
  ——存容器内的话每次重建就归零，等于没有熔断。

⚠️ 这一层与 cluster 的 `maxFastCrashes` 分工不同：那个管**worker 进程**，这个管**容器**
（worker 崩溃会让主进程以退出码 1 结束，然后被这一层计数）。

## 启动失败时的日志长什么样

启动期的失败现在会先分类再打印，不会只丢一坨堆栈：

- **数据库不可达**：`[FATAL][startup] 数据库不可达：…`，附已重试时长，以及三条下一步
  （什么都不做等自动恢复 / 跑 `./vanblog.sh doctor` 体检 / 数据库彻底坏了就用
  `./vanblog.sh restore --offline-full <归档>` 从一份好归档重建）。
- **启动流程本身出错**（不是数据库那条路径）：`[FATAL][startup] 启动流程本身出错…`，
  附原始错误。这两类分开是有意的——它们的处置完全不同。

::: tip 尽力而为的步骤不会打死启动

写哨兵、快照哨兵状态、还原哨兵这些都是**尽力而为**的辅助步骤：它们失败只会让
「降级发布」这一个能力不可用，并打一条说明影响与处理办法的 WARN，
**不会**让站点起不来。真正关键的步骤（注册致命错误处理器、初始化 JWT、创建应用、
监听端口）失败仍然会失败——把一切都包进 `try` 会吞掉真故障，比原问题更糟。

:::

`VANBLOG_BOOTSTRAP_DB_RETRY_WINDOW_MS`（及 `_BASE_MS` / `_MAX_MS`）、
`VANBLOG_CRASH_WINDOW_MS`、`VANBLOG_MAX_FAST_CRASHES`、`VANBLOG_FAST_CRASH_MS`、

⚠️ 所有数值变量都是「**写 `0` 得到默认值，不是关闭**」。

## 与「静态直发」的关系

`VANBLOG_CADDY_SERVE_HTML` 是**正常模式下**的性能开关（让 caddy 绕过 Node 直发 ISR 产物，
实测固定页 3.7–4.5× rps、文章页突发 8.8×），默认关闭。

**降级发布不依赖你打开它**：进入降级驻留时会自动按 `all` 档写哨兵文件，退出时精确还原。
也就是说，即使你从没配过这个变量，数据库挂掉时站点仍然会继续发布已渲染的内容。

⚠️ 哨兵文件由 caddy 在**每个请求**时按存在性判断（不解析内容、不需要 reload），
而正常运行时 `CaddyProvider` 每 60 秒会按你的设置对账一次——这个对账是**安全网**：
你没开 `VANBLOG_CADDY_SERVE_HTML` 时，它不会把站点留在「一直直发旧 HTML」的状态。
降级驻留期间 Nest 没有启动，所以对账不在跑，哨兵不会被删（这正是降级发布能成立的前提）。

## 与多进程（cluster）模式的关系

::: warning ea9547f3 之前，集群模式下降级发布根本无从谈起

别把这一节读成"降级发布在集群下一直是好的"。此前 `VANBLOG_CLUSTER_WORKERS>1` 时，
**没有任何进程是"主实例"**（cluster 的主进程不跑 Nest 应用，而每个 worker 的 `cluster.isWorker` 都是 true），
于是 `WebsiteProvider` 在每个进程里都直接 return ⇒ **前台 Next 子进程没人拉起**：

- `/` 与 `/post/*` 全是 **502**（活体实测）；
- 更关键的是**磁盘上根本没有 ISR 产物**（实测产物数 0），而降级发布的内容来源正是这些产物
  ⇒ 即使降级驻留正常进入，也**没有东西可发**。

修复后由**恰好一个** worker（内部变量 `VANBLOG_CLUSTER_ROLE=leader`）承担这些一次性启动任务。
活体复验（`workers=2`）：`GET /` = **200 / 10.5ms**、进程表里**有 `next-server (v14.2.35)`**、
ISR 产物 **53 个**（= 归档里的文章数）⇒ 降级发布需要的产物在集群模式下确实会被渲染出来。
同一轮的**单进程对照**行为不变（产物、`/` 200、所有进程都没有 leader 角色 ⇒ 走原来的判定分支）。

⚠️ 诚实边界：**"集群模式下数据库挂掉 → 进入降级驻留 → 直发产物"这一整条链没有单独做过活体演练**，
活体验证的是它的前提（产物存在、前台在跑）。降级驻留本身的行为（第 1–5 节那些数字）是在单进程下测的。
:::

⚠️ 另外两条与 cluster 相关、但**不属于**降级发布的行为，别混在一起排查：

- **停机语义**：关停时若有 worker 在宽限期内没退出会被 SIGKILL，此时主进程以 **ExitCode 1** 退出并打一条 FATAL
  （以前是退出 0，编排系统看不出异常）。正常的 `docker stop` / `compose down` 仍退出 0。
- **两层熔断的分工**：下面的[重启风暴熔断](#重启风暴熔断)管的是**容器**，
  cluster 的 `maxFastCrashes` 管的是**worker 进程**。leader worker 崩溃退出时会**让位**，
  由重新拉起的那个 worker 接替主实例职责，所以一次性启动任务不会因为 leader 崩一次就永久失守
  （活体实测到让位与接替的日志，且容器 `RestartCount=0`）。

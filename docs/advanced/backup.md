后台 `站点管理/系统设置/备份恢复` 里有两套东西：

- **整站备份与恢复**：一个压缩包 = 整个博客（数据库 + 评论 + 图片 + 附件 + 自定义页面），推荐用这个。
- **数据导入导出（JSON）**：只有数据库记录，不含任何文件，适合在两站之间搬文章。

## 整站备份（推荐）

点「导出整站备份」，下面这些会打进**一个高压缩归档**：

| 内容 | 说明 |
| --- | --- |
| 数据库全部集合 | 文章、草稿、分类、标签、图床记录、设置、访问统计、API token…… |
| waline 评论库 | 评论与评论用户（同一个 MongoDB 实例里的 `waline` 库） |
| 图床图片 + 缩略图 | `/app/static/img/`（含 `img/thumb/`） |
| 附件 | `/app/static/file/`，见 [附件管理](../features/attachment.md) |
| 自定义页面 | `/app/static/customPage/` |
| 上传的主题 | `/app/static/themes/`（`<id>-<hash8>.css`），见 [主题](../features/theme.md) |

不含（都是可再生或临时的，理由写在 `packages/server/src/utils/fullBackup.ts` 的 `BACKUP_STATIC_FOLDERS` 注释里，并有测试守卫这份分类）：`rss/`、`sitemap/`（启动与每次改动后重新生成）、`tmp/`、`upload-tmp/`（备份/恢复与上传的暂存目录）、`export/`（旧导出包，匿名访问已被 403 拦掉，内容按需重新导出）、日志、Caddy 证书。

> ⚠️ 静态目录下**新增**任何子目录时，必须同时在 `BACKUP_STATIC_FOLDERS`（用户数据）或那份注释的"故意不备份"清单里表态：`packages/server/src/audit-hardening-round3-backup.spec.ts` 会把"代码会建、但两边都没登记"的目录判成失败。主题 CSS 就是因为没人登记而**长期没进归档**的 —— 元数据在库里、文件不在，恢复之后后台显示主题已启用，`/api/public/theme.css` 却返回 **204 + 空样式表**
（读文件失败被 `catch`，所以不是 404、控制台也没有任何报错），前台静默退回默认皮肤。

### 压缩格式

导出时可以选，默认「自动」= 挑本机最强的那个（`zstd` > `xz` > `gzip`）：

| 格式 | 命令 | 特点 |
| --- | --- | --- |
| zstd（默认） | `zstd -19 --long=27 -T0` | 体积最小、速度也快，推荐 |
| xz | `xz -9e -T0` | 体积和 zstd 差不多，慢好几倍 |
| gzip | `gzip -9` | 哪儿都有，体积略大、最快 |

一个真实站点的实测（53 篇文章、90 张图、68.8 MB 静态文件、9779 条文档）：

| 格式 | 归档体积 | 导出耗时 | 恢复耗时 |
| --- | --- | --- | --- |
| gzip -9 | 66.00 MB | 5.4 s | ~3 s |
| **zstd -19 --long** | **65.91 MB** | 33.9 s | ~3 s |
| xz -9e | 65.92 MB | 51.4 s | ~3 s |

::: tip 为什么压缩率看起来不高

图片本身已经是 WebP（压过一遍了），再压只能挤出 1%~2%；真正被压掉的是数据库部分——9779 条文档的 JSON 有好几 MB，压完几乎不占地方。所以想让备份更小，关键是**图床开启 WebP/AVIF 压缩**和[大图自动缩放](../features/image-storage.md#大图自动缩放)，而不是换压缩算法。

:::

### 归档放在哪、怎么下载

归档写在服务器的**备份目录**：默认 `<日志目录>/vanblog-backups`（Docker 里就是 `/var/log/vanblog-backups`，跟着已映射的卷一起持久化）。可以用配置项 `backup.path` 或环境变量 `VAN_BLOG_BACKUP_PATH` 改。

**故意不放在 `/app/static` 下面**：静态目录是匿名可访问的，而备份里有密码哈希和 jwt 密钥。后台列表里的「下载」走鉴权接口，猜 URL 拿不到（直接访问会被拦掉）。

::: warning 归档等于站点凭据，请按凭据保管

`/var/log` 是 **bind mount 到宿主机**的，所以容器里的文件权限就是宿主机上的权限。归档里是整个数据库
—— 全部口令的 scrypt 哈希、`settings` 里的 jwt 密钥、所有文章 —— **拿到归档就等于拿到站点凭据**：
jwt 密钥可以直接签一个管理员令牌，不需要破任何密码。

所以现在写出来的文件权限都是收紧过的：归档、`.sha256` 旁证、`backup-status.json`、事件日志
（**含轮转出来的历史份**）都是 `0600`，备份目录是 `0700`。

⚠️ 本轮之前写的文件是 `0644`/`0755`。那些**已有的归档照读不误**（恢复路径没有收紧，只收紧我们新写的
文件），但把它们拷去异地时请按凭据对待：别放进对象存储的公开桶，别用宽松权限挂载共享目录。

:::

崩溃遗留的中间产物会自动清理：上次备份/恢复没跑完留下的工作目录（`<静态目录>/tmp/full-restore-*`，
里面是**解包后的整站明文**）与上传暂存（`<备份目录>/upload-tmp/restore-upload-*`，单个可达 8GB），
在启动时按 `VANBLOG_BACKUP_STALE_WORK_HOURS`（默认 6 小时，`0` = 关闭清理）清掉——只删够旧的，
正在跑的那次不受影响。⚠️ 这些目录匿名 HTTP 读不到（静态守卫对 `tmp`、`upload-tmp` 一律 403），
所以它治的是"明文落盘 + 每次崩溃漏一份磁盘"，不是远程泄露。参数见[环境变量](../reference/env.md#备份与恢复)。

### 用一键脚本做整站备份（推荐）

```bash
./vanblog.sh backup                     # 整站备份（默认 zstd）
./vanblog.sh backup --format xz         # 换压缩格式：zstd / xz / gzip
./vanblog.sh backup --offline           # 兜底：直接打包数据目录（站点起不来时用）
./vanblog.sh backup --offline --consistent   # 先停 mongo 再打包（一致性好，短暂停机）
```

**默认走的是 server 的整站备份接口**（和后台「系统设置 → 备份」是同一套逻辑），
产出 `vanblog-full-<时间戳>.tar.zst` + 一份 sidecar 清单，落在
`<数据目录>/log/vanblog-backups/`。相比"打包数据目录"，它有三个实打实的好处：

| | 整站备份（默认） | 数据目录 tar（`--offline`） |
| --- | --- | --- |
| 一致性 | 由 server 在运行中导出，**不会拍到 mongod 写了一半的文件** | 热备份不一致；`--consistent` 要先停 mongo |
| 跨版本恢复 | NDJSON，**不绑 MongoDB 版本**（4.4 → 6.0 → 7.0 都能恢复进去） | 数据目录换个大版本 mongod 直接拒绝启动 |
| 可预览 | 恢复前能读清单看每个集合多少条 | 只能整包解开看 |
| 包含 caddy 证书与配置 | ❌ 不含 | ✅ 含（整个数据目录） |
| 需要站点在跑 | ✅ 需要（要调接口） | ❌ 不需要 |

所以：**日常备份用默认的整站备份**；只有在站点起不来、或者你想连 caddy 的证书一起备的时候，
才用 `--offline`。

备份成功后会打印归档名、大小、内容统计（多少个集合 / 多少条文档 / 多少个静态文件）、
**宿主机上的完整路径**，以及对应的恢复命令：

```
整站备份成功
  归档    ：vanblog-full-20260913-181937.tar.zst（65.91 MB，用时 29.9s）
  内容    ：15 个集合 / 9838 条文档 / 185 个静态文件
  宿主机路径：/var/vanblog/data/log/vanblog-backups/vanblog-full-20260913-181937.tar.zst
  恢复    ：./vanblog.sh restore vanblog-full-20260913-181937.tar.zst
```

站点没起时不会偷偷打个 tar 糊弄你，而是明确报错并给出两条路（先 `start`，或改用 `--offline`）。

认证与接口地址的规则和恢复完全一样：`VANBLOG_ADMIN_TOKEN` 优先，否则交互输入账号密码
（本地按后台同一套算法派生口令，明文不出本机）；接口地址默认从编排文件读端口，
也可用 `VANBLOG_API_BASE` 指定。

## 用一键脚本一步恢复（推荐）

整站备份（`vanblog-full-*.tar.zst`）以前只能在后台「系统设置 → 备份」里点恢复，
或者自己调接口。现在 `vanblog.sh` 直接支持：

```bash
./vanblog.sh restore                    # 列出服务器备份目录里的归档，选一个恢复
./vanblog.sh restore vanblog-full-20260913-172338.tar.zst    # 一步恢复（不上传，秒级开始）
./vanblog.sh restore /path/to/vanblog-full-xxx.tar.zst       # 本地文件，走上传
./vanblog.sh restore <归档名> --no-static                    # 只恢复数据库，保留当前图床/附件
```

几个要点：

- **不停服**：恢复走 server 的接口，由它按集合原子替换、重建索引、恢复静态文件，
  最后自动触发一次全量渲染（ISR），前台几分钟内刷新到新数据。
  （老的 `vanblog-backup-*.tar.gz` 是数据目录的原始 tar 包，那条路径仍然要停服解压，脚本会自动分流。）
- **归档已经在服务器上就不用上传**：给"名字"时接口直接读服务器备份目录里的文件，
  几百 MB 也省掉一次传输；给"本地路径"时才 multipart 上传。
- **认证**：默认交互式输入后台账号密码（脚本本地按后台同一套算法派生口令，
  **不会把明文密码发出去**），也可以用 `VANBLOG_ADMIN_TOKEN=<token>` 跳过登录
  （token 在浏览器 F12 → Application → Local Storage → `token`）。
  ⚠️ 登录接口有失败次数限制，脚本**只试一次不重试**，别拿它爆破自己的账号。
- **接口地址**：默认从编排文件里读 vanblog 服务映射到容器 80 的宿主机端口，
  拼成 `http://127.0.0.1:<端口>`；也可以用 `VANBLOG_API_BASE=` 指定（比如站点在别的机器上）。
- **必须显式确认**：恢复会覆盖**全部**数据（数据库所有集合、waline 评论库、图床/附件/自定义页面），
  所以要输入 `yes`；自动化场景用 `VANBLOG_ASSUME_YES=1`。
  ⚠️ **直接调接口时的确认字段只认一种拼写**（2026-09 起）：`confirm` 必须是布尔 `true` 或字符串 `"true"`
  （**区分大小写**）。`"1"`、`1`、`[1]`、`"yes"`、`"TRUE"` 一律**不算确认**，返回 400，报错文案里写明了
  接受哪种拼写。改动前这个闸门用的是全仓库**最宽松**的布尔解析（`confirm:"1"` 也算"是，覆盖一切"），
  而破坏性操作的确认闸门本该是**最严**的那个。后台与一键脚本送的一直是 `'true'`，所以它们不受影响；
  ⚠️ 只有**第三方集成**如果送过 `1`，升级后会开始收到 400。
- 恢复前脚本会先调 `full/inspect` 把**备份清单**打出来（备份时间、各集合条数、静态文件数），
  确认没选错版本再动手。

#### 想自己调接口：整站备份这一组

都在 `/api/admin/backup/` 下，要后台登录态（`token` 头）：`full/formats`（GET，支持哪些压缩格式）、
`full/export`（POST，做一份整站备份）、`full/status`（GET，上一次备份的状态）、
`full/list`（GET，列归档）、`full/inspect`（POST，读某份归档的清单）、`full/restore`（POST，恢复）、
`full/download`（GET，下载归档）、`full/delete`（POST，删一份）。

⚠️ 还有一条 `full/verify`（POST，让 server 复验一份归档），**目前没有任何调用方**：后台界面不用它，
一键脚本的 `backup-verify` / `verify-deep` 也**不走它** —— 那两条是在本机直接验归档
（`zstd -t` + 成员清单 + sha256 + 归档内的 integrity 块），这样站点没起来也照样能验。
`full/verify` 是留给接口调用方的，别把脚本的验证结果当成它给的。

::: warning 清单读不出来时，校验结论会明说「哪些检查根本没做」

`verify` / `backup-verify` 的结论里有一句概括（例如「解包可读、清单可解析、计数对得上」）。
⚠️ 当归档的**清单本身读不出来**时，改动前那句概括仍然会印出来 —— 而清单恰恰**没有**解析成功。
在灾难恢复路径上，一句假的「这项没问题」会诱导站长拿一份**验不了**的归档去覆盖现有数据。

现在这句话有两个版本：清单可读时照旧；清单不可读时会**直说**成员级检查与计数核对**全部没有做**，
并且明确写着「**不要拿这份归档去覆盖现有数据**」，同时指路 `./vanblog.sh backup-verify --all`
去把备份目录里**能验过**的那一份找出来。
:::

还有 `jwt/rotate`（POST，轮换 jwt 签名密钥），见 [安全 → jwt 密钥轮换](./security.md#jwt-密钥轮换)。

::: warning 恢复加密归档时，口令字段名有两个，别搞混

两条恢复接口用的**字段名不一样**，写错会得到 400 或者**静默不解密**：

| 接口 | 谁能调 | 口令字段名 |
| --- | --- | --- |
| `POST /api/admin/backup/full/restore` | 管理员（`vanblog.sh restore` / `reset` 走的就是这条） | **`passphrase`** |
| `POST /api/admin/init/restore` | **匿名**（站点还没初始化的窗口，初始化页那张「已有整站备份？直接恢复」卡片） | **`backupPassphrase`** |

两条都**只从 body 取**（JSON 或 multipart 的文本字段都行），⚠️ **都不接受查询参数** —— query 会被写进 caddy 的访问日志，等于把口令留在磁盘上。

⚠️ **口令留空时恢复流程会自己去读环境变量**：容器里配了 `VANBLOG_BACKUP_PASSPHRASE`（或 `_FILE`）的话，脚本不送口令也能恢复。这对「编排里配好口令」的部署与 `drill` 演练是关键兜底 —— 演练时不需要把口令再传一遍。

:::

### 归档加密（可选，默认关）

整站归档里有**整个数据库**：所有账号的口令哈希（scrypt）、`settings` 里的 jwt 签名密钥、文章与评论、图床凭据。⚠️ 也就是说**拿到归档 ≈ 拿到站点凭据** —— 用 jwt 密钥可以直接自签一个管理员令牌，不需要破解任何口令。所以归档要按凭据保管（目录 0700、归档 0600，bind mount 下容器权限就是宿主机权限）。

如果归档还要放到**你不完全控制的地方**（对象存储、异地备份盘、别人给的网盘），就打开加密：

```yaml
# docker-compose.yaml 的 vanblog 服务下
environment:
  - VANBLOG_BACKUP_PASSPHRASE_FILE=/run/secrets/vanblog_backup_passphrase
secrets:
  - vanblog_backup_passphrase
```

或者直接用内联变量 `VANBLOG_BACKUP_PASSPHRASE`（简单，但口令会出现在编排文件与 `docker inspect` 里，所以更推荐上面的 secret 文件方式）。设好之后重启容器，下一次备份就是加密的。

它的行为，逐条都值得知道：

- 归档名多一个 **`.enc`** 后缀：`vanblog-full-<时间戳>.tar.zst.enc`。⚠️ 但**格式判别一律以文件开头的魔数 `VANBLOGENC1` 为准**，后缀只用于展示与通配 —— 站长完全可能把归档改名，靠后缀判断会出错。
- **`.sha256` 与 `.manifest.json` 这两个 sidecar 保持明文**：这样**不解密也能校验完整性**（`./vanblog.sh verify` 与 `doctor` 都还能正常工作）。
- 加密是**分块 AES-256-GCM**（1 MiB 一块，内存恒定），密钥由口令经 scrypt 派生。每块自带认证标签，所以**篡改任何一块都会被发现**，不是"只保机密性"。
- `backup-status.json` 里多了两个字段：`lastSuccessEncrypted`（布尔或 `null`）与 `lastSuccessEncryption`（KDF 参数摘要，非机密）。⚠️ **`null` 不等于 `false`**：`null` 表示"这次成功备份早于本功能，不知道当时加没加密"，`false` 才是"确定没加密"。
- **口令最短 12 字节**，短了**备份直接失败** —— 宁可不产出，也不写一份能离线爆破的弱归档。
- ⚠️ **口令强度只在加密时校验，解密时不校验**：否则哪天把最小长度调高，旧归档就读不出来了。
- 每次备份成功而**没有**加密时，会打一条 WARN 说明现状与怎么开。

::: danger 忘了口令 = 归档永久不可恢复

没有后门、没有找回、没有"用管理员身份重置"。**加密归档必须至少成功演练过一次才算备份可用**：

```bash
./vanblog.sh drill        # 真起一次性栈恢复一遍，证明这份归档能恢复成一个能用的站点
```

另外两条实操建议：①口令本身也要有离线副本（密码管理器 / 抄下来放保险柜），它和归档**不要放在一起**；②开了加密之后，`drill` 要能读到口令 —— 要么给演练环境也配上 `VANBLOG_BACKUP_PASSPHRASE(_FILE)`，要么在跑 `drill` 时把口令传进去。

:::

### 离线签名（可选，默认关）

它要回答的问题是：这份归档**有没有被换成另一份**。

归档旁边本来就有 `.sha256` 与 `.manifest.json`，但它们和归档**在同一个目录**：
能替换归档的人也能替换它们。所以那两样只能证明归档**自洽**（没拷坏、没截断），
证明不了它**没被人换成另一份**。签名补的就是这一环。

用 Node 内置的 **ed25519**（不引入任何新依赖），签名是**分离式**的：归档旁边多一个
`<归档名>.sig`，明文 JSON、权限 `0600`，里面有整档的 sha256、字节数、**公钥指纹**、
签名时间、64 字节的签名，以及归档文件名。

几条性质值得知道：

- 🔴 **加密归档签的是密文**（顺序是 `tar → zstd 压缩 → 加密（可选）→ 流式算 sha256 → 签名`），
  所以**不解密也能验真**：一台只做恢复的机器只需要公钥，不需要备份口令。
- **归档文件名不参与签名**，所以运维改名不影响验签（校验一律以内容 sha256 为准）。
- 签名**不覆盖机密性**：加不加密是 `VANBLOG_BACKUP_PASSPHRASE` 的事，两者独立。
- 三种 sidecar（`.sha256` / `.manifest.json` / `.sig`）与归档**同生共死**：
  异地镜像会一起拷过去，保留策略清理时会一起删。
  ⚠️ 这一点很要紧——`.sig` 的名字是 `<归档名>.sig`，它会被 `vanblog-full-*` 这类通配匹配到，
  如果清理逻辑不认它，就会出现「sidecar 占掉 `--keep` 名额、真归档被提前删掉」的数据丢失，
  而且命令返回 0、日志一切正常。

::: danger 信任边界（务必照实理解，别把它当成更强的东西）

**验签材料（公钥）必须存在主机之外**，否则这个功能等于没做。具体地：

- 它防的是「归档**离开主机之后**被篡改」——上传到对象存储、拷进网盘、写到 U 盘、
  同步到异地副本、交给另一台机器去恢复：这些路径上任何一环被动手脚都能被发现。
- 它**不防**已经拿到**主机 root** 的攻击者：私钥必须在主机上（否则没法签名），
  有 root 就能读私钥、重新签一份、把归档和 `.sig` 一起换掉，验签照样通过。
  同理，把公钥也存在同一台主机上（且攻击者能写）时，他可以连公钥一起换。
- 所以正确用法是：**公钥的权威副本离线保存**（密码管理器 / 打印 / 另一台机器），
  恢复时用它来验，而不是用主机上那份。

这段文字也会原样出现在后台接口的响应里（`trustBoundary` 字段）——因为这个功能最危险的
失败模式是**被高估**：以为「签了名就万无一失」，于是把归档和公钥扔进同一个网盘。

:::

#### 怎么开

三选一（优先级从上到下）：

```bash
# ① 让服务端生成一对密钥（私钥落在 <备份目录>/signing/，权限 0700/0600）
./vanblog.sh signing-key
./vanblog.sh signing-export > vanblog-backup.pub.pem   # 公钥走 stdout，拿去离线保存

# ② 自己生成、用环境变量或文件挂进来（Docker secret / k8s Secret 的标准用法）
VANBLOG_BACKUP_SIGNING_KEY_FILE=/run/secrets/vanblog-signing.pem
VANBLOG_BACKUP_VERIFY_KEY_FILE=/run/secrets/vanblog-verify.pub.pem

# ③ 内联 PEM（不推荐，会进编排文件）
VANBLOG_BACKUP_SIGNING_KEY="-----BEGIN PRIVATE KEY-----..."
```

⚠️ `_FILE` 形式**优先**于内联形式；只去掉结尾换行；🔴 **读不到就失败关闭**
（不会静默回落到「不签名」——那会让你以为签了其实没签）。
⚠️ **什么都没配就完全不签名**，行为与以前逐字节一致，既有部署零影响。

对应的后台接口都在超管专属前缀下（勾了「所有权限」的协作者碰不到）：
`GET|POST /api/admin/backup/signing/key`（导出公钥 / 生成密钥对，🔴 **私钥绝不经过任何接口返回**）、
`GET /api/admin/backup/full/download-sig?name=<归档名>`（下载某个归档的 `.sig`）。
后台「备份与恢复」列表的操作列也有一个「签名」动作。
⚠️ 归档没签过时它返回 **404**，含义是「**这份归档从没被签过**」，**不是**下载失败。

::: warning 覆盖已有密钥会让所有旧签名永久失效

`signing-key` 在已有密钥时**拒绝改动并非 0 退出**，除非显式给 `--overwrite`。
原因是覆盖之后，**所有旧归档的 `.sig` 都验不过了**（内容没问题，只是没有对应的公钥了）。
所以它会先把「导出旧公钥」的命令给你。目前不支持「多把公钥同时可验」的轮换。

:::

#### 验签结论有五种，必须分得清

`POST /api/admin/backup/full/verify` 的响应里有 `signature` 段，`./vanblog.sh verify --server-signature`
会把它翻译成人话。⚠️ 五种结论的处置**完全不同**，混成一句「校验失败」会让人在灾难现场做错决定：

| 状态 | 含义 | 该怎么办 |
| --- | --- | --- |
| `ok` | 签名验过了 | 可以用这份归档恢复 |
| `mismatch` | 指纹对得上但签名验不过 ⇒ **归档或 `.sig` 在签名之后被改动过** | 🔴 **不要用这份归档恢复**，换一份，或用 `backup-verify --all` 找出最近一份校验通过的 |
| `key-mismatch` | `.sig` 是**另一把密钥**签的 ⇒ 归档不一定有问题，更可能是**你手上的公钥不对** | 找回签名时那把密钥对应的公钥（离线副本 / 密码管理器），配到 `VANBLOG_BACKUP_VERIFY_KEY(_FILE)` 后重试 |
| `missing-sig` | 这份归档**从没被签过**（早于本功能，或备份时没配密钥） | 谈不上真假——只能靠 `.sha256` / 完整性清单证明它**自洽** |
| `no-key` | 有 `.sig` 但本机没有可比对的公钥 ⇒ **这次没有真验签** | ⚠️ 别把它读成「验过了」；配上公钥再验 |

区分 `mismatch` 与 `key-mismatch` 靠的就是 `.sig` 里的**公钥指纹**——ed25519 验签失败本身分不出这两种。
⚠️ `missing-sig` 与 `no-key` **只记 note、不算 issue**：否则所有老归档会全线报红，
而一个永远红的报告训练出来的是「忽略红」。

⚠️ 脚本侧的 `./vanblog.sh verify`（不加 `--server-signature`）**不做密码学验签**，
它只报三态（已签名 / 从没被签过 / `.sig` 形状不对）并明说这一点。
这是有意的：在 bash 里重写一遍 ed25519，写错的失败方向是**假通过**，比不验更危险。
`--server-signature` 之所以不是默认，是因为权威验签要把整份归档流式哈希一遍，
对 `--all` 的每份归档都打服务端会让 I/O 翻倍。

#### 恢复时的闸门

签名校验是恢复流程的**第 0 道闸门**（排在读成员表与解包之前）：

| 情况 | 行为 |
| --- | --- |
| 配了公钥 + 有 `.sig` + 验得过 | 放行 |
| 配了公钥 + 有 `.sig` + **验不过** | 🔴 **拒绝恢复（400）**，报错里给出逃生口的名字 |
| **没配公钥** | **放行 + WARN**（⚠️ 绝不能变成拒绝，否则所有既有部署升级后就恢复不了了） |
| 配了公钥但**这份归档没签过** | **放行 + WARN**（历史归档不能变成新的锁死来源） |
| 显式给了跳过开关 | 放行 + WARN，并明说跳过了什么 |

跳过验签的开关是 `./vanblog.sh restore` / `reset` 的 **`--skip-signature-check`**（位置参数）。
🔴 **它刻意不做成环境变量**：环境变量意味着 cron、编排文件、甚至 `VAR=1 ./vanblog.sh restore`
这种一次性前缀都能**静默**打开这个绕过，而绕过验签的后果是「恢复了一份被换过的归档，
而且整个过程显示成功」。服务端那侧也只认字面量 `true`（送 `1` 不算）。

⚠️ **匿名恢复路径（初始化页 / `POST /api/admin/init/restore`）没有跳过开关**——这是有意的：
一个匿名可达的接口不该带着绕过安全校验的入口。它接受一个可选的 `signature` 字段
（curl 写 `-F "signature=<路径>"`，⚠️ 是**文本字段**，用 `@` 会变成文件字段而服务端读不到），
不带就跟以前一样。

::: tip 为什么签名密钥不从备份口令派生

`VANBLOG_BACKUP_PASSPHRASE` 已经存在，用它 scrypt 派生一个 ed25519 种子在技术上完全可行，
但**故意没有那么做**：那样「验签」就需要口令，而**任何持有口令的一方都同时能签名** ⇒
异地副本 / DR 主机为了验签就得拿到口令，也就获得了伪造能力，非对称签名的全部意义
（验证方无法伪造）当场消失。附带好处是「加密口令泄露」与「签名密钥泄露」是两件独立的事，
不会一次性双双失守。

:::

### 证明备份真的能恢复：`./vanblog.sh drill`

> **为什么需要它**：`verify` 只能证明"这个文件是完整的"（`zstd -t` + 成员清单 + sha256），
> **证明不了"它能被恢复成一个能用的站点"**。这两件事差得很远 —— 本项目就踩过两次：
> 一次是恢复直接报 `Unsupported BSON version`（编解码用的 BSON 构造器与写库的驱动不是同一个大版本），
> 一次是**上传的主题 CSS 从来不进归档**（元数据在库里、文件不在，恢复后后台显示主题已启用而 CSS 是空的）。
> 两次都是"备份看着成功、恢复才发现坏了"，而 `verify` 一次都没报警。

```bash
./vanblog.sh drill                                   # 用备份目录里最新的那份
./vanblog.sh drill /path/vanblog-full-xxx.tar.zst    # 指定一份
./vanblog.sh drill <归档> --dry-run                  # 只打印计划、不建任何容器（⚠️ 仍会探测容器引擎，机器上没有可用的 docker/podman 时会报 FAIL）
./vanblog.sh drill <归档> --keep                     # 演练完把一次性栈留着，打印怎么访问、怎么拆
./vanblog.sh drill <归档> --image vanblog:local-test # 指定被测镜像
```

它会起一套**一次性**的 mongo + vanblog（命名卷、容器 IP + `--add-host`、临时端口、与线上栈完全隔离，
mongo 端口永远不选 27017，`trap` 保证任何失败路径都清理干净），
等健康检查通过，然后**真的**把归档上传到 `POST /api/admin/init/restore`（也就是用户会走的那条生产路径，
不是内部函数调用），再断言**语义**：

| 断言 | 为什么这条重要 |
| --- | --- |
| 信封 `statusCode:200`、`counts.articles > 0` | 恢复接口本身通了 |
| **信封里的 counts 与归档 manifest 对账**、manifest 自身求和一致 | "接口说恢复了 59 篇"与"归档里写了 59 篇"是两件事 |
| meta 是真实站点（不是未初始化的 233 信封） | 站点信息真的回来了 |
| **公开列表的 total == 从归档自己的 `articles.ndjson` 逐文档数出来的公开篇数** | 这是最硬的一条：它证明"库里的东西"与"归档里的东西"一致，而不是接口自己报了个好看的数字 |
| 一个真实静态文件 200 且非空 | 图床/附件真的落盘了 |
| **主题 CSS 能否取到**（归档里有 `static/themes/` 时） | 上面那次"主题不进归档"的回归，从此有真机覆盖 |
| 容器日志里没有 BSON 指纹 / 模块缺失 / unhandledRejection | 静默失败也算失败 |
| **第二次恢复必须 403** | 已初始化的站点不该再被这条匿名路由覆盖 |

上传时 drill 会**自动带上初始化密钥**：新版接口默认要求 `setupKey` 字段，drill 从一次性容器里的
`/var/log/setup.key` 读（读不到再从容器日志里那行「初始化密钥：」兜底），你不需要手工提供，
密钥也不会出现在命令行或演练输出里（只报字节数）。

最后一行是机器可读的，方便接进 CI 或 cron：

```
RESULT: PASS pass=37 warn=1 fail=0 note=5
```

（`pass` 的条数会随着断言增加而变多，**不必和这里对上一模一样**；要看的是 `fail=0`。）

真机结果（podman 4.9.3 rootless、一份 69,111,118 B ≈ 65.9 MiB 的归档）：mongod 就绪约 4 秒、
服务就绪约 6 秒（`/api/public/health` 200，mongo ping 2ms）、恢复 **HTTP 201 / 服务端 3.1 秒 /
端到端 4 秒**、写入 **9838 条文档 / 13 个集合**、公开列表 `total 53 == 53`（归档共 59 篇，其中 6 篇是软删的）、
一个真实静态文件 `GET /static/img/…webp → 200, 823,370 B`、静态树逐文件一致（**归档 185 个文件全部在、一个不多**
⇒ 顺带证明了"恢复会修剪静态目录"这条默认行为）、第二次恢复 403、演练后 0 个残留容器/卷/网络。
这一份归档早于「主题进整站备份」那个修复，所以主题那条是 **WARN + note** 而不是 PASS（见下）。
如果换成修复之后导出的归档，还会多一条 `/static/themes/<id>-<hash8>.css → 200` 且字节数与 manifest
记的 `themes.bytes` 相符。

⚠️ 早于"主题进归档"那次修复的归档，drill 会把缺失的 `static/themes/` 报成**信息性 note**
（"这份归档早于主题备份，真机恢复会丢上传的主题"）而不是静默通过 —— 因为它确实会丢。

**坏归档也要演练**（`--skip-preflight` 让它真的走到端点）：截断的归档应该得到 **HTTP 400 + 退出码 1 + 完整清理**，
而且**紧接着的好归档演练必须仍然通过**。后面这半句才是重点：曾经有个 bug 是坏归档会让恢复接口的
单飞锁**永久卡死**（`listArchiveMembers` 在截断归档上永不 settle），于是"上传一个坏归档就能让整站再也恢复不了"，
只有这个"坏归档之后还能恢复"的断言能抓到它。

### 相关的四个子命令

| 命令 | 要 root 吗 | 做什么 |
| --- | --- | --- |
| `./vanblog.sh verify <归档>` | **要** | 老命令，**行为不变**：只查结构（解压器自检、成员清单、sha256 边车），宽松。⚠️ 故意不升级成严格版，因为那会静默改掉现有 cron 的退出码 |
| `./vanblog.sh verify-deep [归档…]` | 不要 | 先跑一遍 `verify`（输出行逐字保留），再加**语义层**：manifest 必须能**从归档内部**读出（只有边车不算，因为恢复读的是内部那份）、`kind` 对不对、`version > 1` 大声失败（比本程序新的格式恢复时会被拒）、每个声明的集合都有对应 `.ndjson`（缺 = WARN）、有没有不安全的成员路径（绝对路径或任何 `..` 段 = FAIL）、计数非零且自洽、`static/themes/` 在不在（不在就 WARN 并说清后果）、需要哪个解压器以及本机有没有、上传文件名白名单 |
| `./vanblog.sh backup-verify` | 照 `backup` | 备份 → 用**目录差分**找到新归档 → 深度校验 → 陈旧检查 → 写台账 →（可选 `--drill`）。任何一步失败都非零退出，并明说"旧归档没有被清理"。**适合放进 cron**（`install-cron` 默认写的仍是 `backup`，要更严就自己改成这个） |
| `./vanblog.sh backup-status` | 不要 | 回答"上次备份什么时候成功的、校验过没有"：文件系统 + 追加式台账 `<备份目录>/vanblog-verify-log.jsonl` + 服务端的 `backup-status.json`，**都不需要 token**；设了 `VANBLOG_ADMIN_TOKEN` 时才把 `GET /api/admin/backup/full/status` 当第三方意见，**两边不一致本身就是 WARN** |

#### 这几个命令的参数

下面这些开关**只在 `--help` 里有**，别处没写，所以集中列一次（命令行开关优先于同名环境变量；
变量清单见 [环境变量 → 备份与恢复](../reference/env.md#备份与恢复)）：

| 命令 | 参数 | 作用与默认 |
| --- | --- | --- |
| `verify-deep` / `backup-verify` | `--all` | 除了显式给的归档，再把备份目录里的**全部**归档都查一遍（去重）。定期复验就用它 |
| `backup-verify` | `--drill` | 校验通过后**顺手做一次真恢复演练**（等于再跑一遍 `drill`）。最严的一档，也最慢 |
| `backup-status` | `--strict` | 最新归档在台账里**没有"已验证"记录**时也算失败（非 0 退出）。⚠️ 放 cron / 监控里就该加这个，否则"从来没校验过的备份"会被判成正常 |
| `backup-verify` / `backup-status` | `--stale-days N` | 最新归档超过 N 天算陈旧失败。不传就用环境变量的值，再默认 **7**；`0` = 不查 |
| `backup-verify` / `backup-status` | `--reverify-days N` | 任何保留归档距上次"验证通过"超过 N 天算过期。不传就用环境变量的值，再默认 **0 = 关**；配合 `--all` 当定期复验护栏 |
| `backup-verify` / `backup-status` | `--no-stale-check` / `--no-reverify-check` | 分别关掉上面两项检查（比设成 `0` 更直白） |
| `drill` | `--image <ref>` | 演练用哪个 vanblog 镜像。默认：编排文件里那个 → `VANBLOG_IMAGE_REF` |
| `drill` | `--http-port N` / `--mongo-port N` | 指定端口。默认从 **18500** 起往上找空闲的（试 400 个，避开 3000/3001/3002/18080/27017） |
| `drill` | `--mongo-image <ref>` | 演练用哪个 mongo 镜像，默认 `mongo:7.0` |
| `drill` | `--engine docker\|podman` | 指定容器引擎。默认自动探测（docker daemon 连得上用 docker，否则 podman） |
| `drill` | `--prefix <名字>` | 一次性容器/卷/网络的名字前缀，默认 `vb-drill` |
| `drill` | `--timeout <秒>` | 等服务就绪的秒数，默认 **240** |
| `drill` | `--keep` | 演练完**不拆**一次性栈，并打印怎么访问、怎么拆（排查用） |
| `drill` | `--dry-run` | 只打印计划、不建任何容器。⚠️ 仍会探测容器引擎，机器上没有可用的 docker/podman 会直接失败 |
| `drill` | `--no-pull` | 镜像不在本地就**直接失败**，不尝试 pull（离线机器 / CI 用） |
| `drill` | `--skip-hash` | 跳过成员级哈希比对（会打 WARN，结论行也会注明"不含逐成员比对"） |
| `drill` | `--skip-preflight` | 跳过**归档侧的静态预检**（清单/成员表读不出来也照样上传、文件名不合白名单也照样传），用来验证 **server 侧的护栏**会不会挡住 —— 期望的就是恢复接口回 400 |
| `drill` | `--as <文件名>` | 用别的文件名上传这份归档，用来试上传名白名单。会记一条 WARN 提醒"真实用户拿到的是原名" |

⚠️ 一个容易误会的点：`./vanblog.sh verify <归档>`（老的宽松版）**不认识任何 flag**，
多写的开关会被静默忽略；`vanblog-drill.sh verify` 则会打一行黄字「忽略未知开关」。
所以 `verify --strict` 这种写法**不会生效**，要严格请用 `backup-status --strict` 或 `verify-deep`。

服务端那边也做了对应的事：**每次导出（手动与 cron 都算）写完就自校验**（成员级哈希，
默认开启），失败会返回 HTTP 400、把状态记进 `<备份目录>/backup-status.json`
（⚠️ 故意不写进数据库 —— 恢复会把库覆盖掉，状态跟着回退就等于"恢复之后看不到恢复之前
那次备份失败了"）、打一条带原因的 ERROR；此外还有一个**定期巡检**（默认每 24 小时一轮、
每轮最多查最新 3 份，默认只做便宜的结构校验），以及"太久没有已校验的成功备份"的启动告警
（`VANBLOG_BACKUP_STALE_WARN_HOURS`，默认 48 小时，`0` = 关）。
这一整套的开关与节奏（完整性数据、深度校验、巡检、告警）都有环境变量可调，
见 [环境变量 → 备份与恢复](../reference/env.md#备份与恢复)。

### 在新机器的初始化页直接恢复（不用先建管理员）

全新安装不必先走完初始化向导再到后台恢复：初始化页可以直接上传一份 `vanblog-full-*.tar.zst`，
接口是 `POST /api/admin/init/restore`（multipart 字段名 `file`，无需登录，**只在站点还没初始化时开放**）。
它会恢复数据库 + 静态目录（图床、附件、自定义页面、主题），然后自动拉起评论服务、按恢复后的库重启前台、
触发一次全量渲染（含 RSS 与 sitemap），返回里的 `counts` 就是这次恢复进来的条数。
⚠️ 新版**默认还要求初始化密钥**（`setupKey` 字段）：初始化页会自动出现密钥输入框，
密钥在日志目录 `setup.key` 与启动日志里，见 [初始化 → 初始化密钥](../guide/init.md#初始化密钥setup-key)。

几条要知道的：

- **看 `data.initialized`，不要只看 HTTP 200**：归档里没有 `users` 时恢复会成功，但站点仍然是"未初始化"，
  这时应该继续走向导创建账号。
- 已经初始化过的站点会被拒（403），请登录后用后台的「备份与恢复」。同时只允许一个恢复在跑（第二个 409）。
- 上传前会校验：文件名要形如 `vanblog-full-20260913-140955.tar.zst`、能读出清单、
  且归档成员里没有绝对路径或 `..`（防穿越，不依赖 tar 的具体实现），**软链成员与不安全的
  硬链一律拒绝**（软链被拷进静态目录后会被 web 层跟随 = 匿名任意文件读）。
  任一条不过就是 400，**此时还没写过任何数据**。
- **老归档照样能恢复**：清单里缺 `static/themes` 之类的字段只会"少恢复那部分"，不会失败；
  只有"归档版本比本程序新"才会被拒绝。
- ⚠️ **带第三方依赖的流水线要再重启一次**：恢复会立刻按库里的数据把流水线脚本写回 `<codeRunner>/`，
  但依赖安装（`pnpm add`）只在启动时做、不在请求路径上跑。响应里的 `needsRestartForPipelineDeps: true`
  就是这个意思；不重启的话，只用内置能力的流水线可以跑，`require()` 第三方包的会报 MODULE_NOT_FOUND。

## 恢复

两个入口，效果一样：

1. 备份列表里点 **恢复**（用服务器上已有的归档）；
2. **上传备份并恢复**（把别的机器导出的归档传上来，几百 MB 也没问题，走磁盘临时文件不吃内存）。

恢复是「先临时表、再原子替换」的做法：每个集合先导进 `<集合名>__vanblog_restore`，全部写成功后才替换原集合，并按备份里记录的定义**重建索引**；静态文件覆盖回原目录。中途失败原数据还在，也不会留下半张表或临时集合。

两条**默认行为**值得单独说（都有环境变量可关，全表见 [环境变量 → 备份与恢复](../reference/env.md#备份与恢复)）：

- **静态目录会被修剪成与归档完全一致**（默认开）：四个静态目录（`img`、`file`、
  `customPage`、`themes`）里归档中不存在的文件会在**所有拷贝成功之后**被删掉。
  这是「100% 保真恢复」的代价 —— 恢复后不保留「备份之后新上传的图片」。
  想要旧的「只覆盖、不删多余」行为，给容器设 `VANBLOG_RESTORE_PRUNE_STATIC=false` 再重启。
- **归档里缺失的集合只报告、不删除**（默认）：库里有而归档里没有的集合会出现在恢复报告里，
  但不会被 drop。要「恢复成与备份那一刻完全一致的库」，给容器设
  `VANBLOG_RESTORE_DROP_ABSENT_COLLECTIONS=true`（⚠️ 这会**删掉**那些集合，比如归档早于某个
  新功能时，该功能的表就会被清空）。

::: warning 恢复会覆盖当前站点

- 数据库、评论、图床/附件/自定义页面文件**全部按备份覆盖，不可撤销**；动手前先导出一份当前的。
- 恢复完**需要重新登录**：登录态（tokens 表）和 jwt 密钥都来自备份。
- 建议顺手重启一次 server 进程，清掉内存缓存。
- 只认本功能导出的 `vanblog-full-*.tar.zst` / `.tar.xz` / `.tar.gz`；一键脚本 `--offline` 打的**目录级** tar 包
  （`vanblog-backup-*.tar.gz`，里面是 MongoDB 原始数据文件）不能从这里导入，只能用
  `./vanblog.sh restore <文件>` 离线恢复，见 [备份与迁移](../guide/backup.md)。

:::

### 站点已经起不来了，怎么恢复？

平时用的 `restore` 与 `reset` 都要先访问站点接口，而站点要连得上数据库 —— 所以**数据库损坏时这两条路都走不通**。这是个死锁，不是「再试一次」能解决的。这种情况用：

```bash
./vanblog.sh restore --offline-full /路径/vanblog-full-20260920-030000.tar.zst
```

不带归档路径也行（`./vanblog.sh restore --offline-full`），它会列出备份目录里的归档让你挑。

它会依次做四件事，动手前先把清单打给你看、要你输 `yes`：

1. **先校验归档** —— ⚠️ 校验发生在任何改动之前，**校验不过就一个字节都不动**（这时它会建议你换一份归档，或用 `./vanblog.sh verify-deep <归档>` 看细节）；
2. **停栈**；
3. 把数据库目录**改名保留**：`<数据目录>/data/mongo` → `data/mongo.broken-<时间戳>`，⚠️ **是改名不是删除**；
4. **起栈**（站点这时会显示「未初始化」，**这是预期的**）→ 用归档重置整站（初始化 + 恢复 + 重启 + 逐项核对）。

**看到什么算成功**：最后打印 `✓ 离线恢复完成`，前台首页能打开、后台能登录。

**中途失败怎么办**：每一步失败都会打印**可以直接照抄的回滚命令**（核心就是把那个 `.broken-*` 目录改回 `data/mongo`，再 `./vanblog.sh start`）。⚠️ 在确认站点正常之前**不要删**那个目录 —— 它是唯一的回滚点。

::: tip 为什么是「移开坏库 + 走既有 reset」，而不是脚本自己灌数据

自己灌数据等于把「临时集合 → 原子替换 → 重建索引 → 静态文件回位 → 完整性校验」再实现一遍，而这些在服务端已经写好并被大量测试覆盖。重复实现只会得到第二套需要维护、而且**只在灾难现场才被第一次使用**的代码 —— 那是最坏的组合。所以这里做的是把人工手术自动化，每一步都可回滚，绝不留下「半新半旧」的数据目录。

:::

另外：`restore` 与 `reset` 在「站点接口不通」时，现在也会把这套剧本**完整打印出来**（以前只有一句「先 start」，而那在数据库坏掉时恰恰做不到），不用翻文档。

### 后台、一键脚本、目录级快照：三种备份怎么选

`./vanblog.sh backup` 现在**默认就是调这里的整站备份接口**，产物完全一样，
区别只是"在后台点鼠标"还是"在宿主机敲命令"（脚本适合定时任务，还能顺手把归档路径打出来）。

| | 整站备份（后台 / `vanblog.sh backup`） | 目录级快照（`vanblog.sh backup --offline`） |
| --- | --- | --- |
| 产物 | `vanblog-full-*.tar.zst`（NDJSON + 静态文件 + 清单） | `vanblog-backup-*.tar.gz`（整个 `/var/vanblog` 目录） |
| 一致性 | server 运行中导出，一致 | 热备份不一致；`--consistent` 要先停库 |
| 含 MongoDB 原始文件 | ❌（逐集合导出，跨版本更安全） | ✅（恢复时 mongod 版本必须对得上） |
| 跨版本/跨部署方式恢复 | ✅ 脚本部署 ↔ Docker 都行 | ⚠️ 受 mongod 版本与 FCV 限制 |
| 含 caddy 证书与配置 | ❌ | ✅ |
| 需要站点在跑 | ✅（要调接口） | ❌ |
| 恢复是否停服 | 不停（恢复完自动触发全量渲染） | 停（解压覆盖数据目录） |
| 体积 | 更小（高压缩） | 更大（含数据库文件与日志） |

**日常用整站备份**；`--offline` 是"站点起不来"或"要连证书一起搬机器"时的兜底。

## 导出单篇文章（含图片）

后台「文章 / 草稿」列表每行的**导出**、以及编辑器里的**导出**，现在都是一个**下拉三选一**
（以前点一下**永远**得到一个外层 zip，想要一个能直接拖进 Typora/Obsidian 的 `.md` 还得先解包）：

| 选项 | 拿到的文件 | 什么时候用它 |
| --- | --- | --- |
| **Markdown (.md)** | `<标题>.md`，正文原样，**图片链接仍指向站点** | 只要文字、或要粘到别处继续写。⚠️ 服务端此时**完全不抓图**，所以最快，也不会去碰任何外链 |
| **Typora 图片包 (.mdz)** | `<标题>.mdz`（一个 zip）= 链接改成相对路径的 md + `<标题>.assets/` 图片目录 | 要**离线**打开、或搬到别的编辑器/仓库。⚠️ 正文没有图片时服务端会回 400 说明原因（那种情况 .mdz 与 .md 等价），不会静默改发 .md |
| **全部打包 (.zip)** | `<标题>-markdown.zip` = 原样 `.md` + `.mdz`（有图才有）+ `导出说明.md`（有跳过/失败的图才有） | 一次拿全，也是**一直以来的行为**（不传 format 就是它，所以老脚本/老前端不受影响） |

同一篇文章三种格式的实际大小（一篇带 1 张图的文章）：**.md 9,908 B / .mdz 46,587 B / .zip 51,257 B** ——
只要文字时选 .md 能少下载 5 倍。

接口是 `POST /api/admin/export/markdown`，请求体多了一个可选的 `format`（`md` / `mdz` / `zip`）：

- **未知格式明确回 400**（`不支持的导出格式：pdf（只支持 md / mdz / zip）`），不静默回落到 zip ——
  调用方写错字段名时，一句 400 比"莫名其妙拿到一个压缩包"好查得多。
- 三种格式都带 `X-Export-Report` 响应头（识别到几个图片引用、打了几张、跳过/失败几个），
  前端据此解释结果；报告里还有一个 `assetsPacked` 字段，**用来区分"这个格式本来就不含图片"与"想打包但失败了"**
  —— 少了它，选 .md 导出带图文章会弹出「有图片没打进包」，看着像出了错。
- 临时目录在**每种格式**发完之后都会删掉（以前只对 zip 那条路径负责）。

> 批量导出（列表页勾选多篇 → 「批量导出」）是**另一条路**：它在浏览器端把每篇转成 `.md` 直接下载，
> 不经过服务端、不含图片、也不需要解包。要连图片一起带走，请逐篇用上面的 .mdz。

`.mdz` 是**往返格式**：编辑器的「导入内容」可以直接把它导回来（图片走正常上传管线入图床、
相对链接改写成图床 URL、Front Matter 里的 `password` 丢弃），见 [文章管理 → 导入文章](../features/article.md#导入文章)。

### 选「全部打包 (.zip)」时，包里有什么

入口在 `内容管理/文章管理`（或 `草稿管理`）每一行的**导出**下拉，以及编辑器右上角的
「导出文章 / 导出草稿 / 导出关于」：

| 文件 | 内容 |
| --- | --- |
| `<标题>.md` | **原样**导出的 Markdown：front matter（标题、别名、分类、标签、时间、隐藏/密码等）+ 正文，图片链接仍指向站点地址 |
| `<标题>.mdz` | 有图片时才生成。本质是个 zip（改后缀就能解开）：里面是图片链接已改成**相对路径**的 `<标题>.md`，加上 `<标题>.assets/` 图片目录 —— Typora 风格，解压后双击 md 就能连图一起看 |
| `导出说明.md` | 有图片没打进包时才生成：列出跳过（data URI、无法定位的相对路径）和失败（防盗链、超时、地址失效）的图片 |

几点说明：

- **图片怎么来的**：本站图床里的图片直接读服务器磁盘；带自己域名的绝对地址也算本地图。
  站外图片会尝试抓一次（超时 15 秒、单张上限 50 MB、最多 3 次重定向），抓不到就保留原链接，
  并在 `导出说明.md` 里列出来。内网地址一律不抓（防止借导出探测内网）。
- **文件名**：标题里的空格和 `()[]{}'"#%` 会换成 `-`（否则 markdown 链接需要转义，各家编辑器支持程度不一）；
  标题原文仍在 front matter 里，导入回来不会丢。
- **编辑器里未保存的改动也能导出**：编辑器导出用的是当前编辑区内容（所见即所得），
  front matter 取自已保存的那份。关于页没有文章 id，走「直接打包当前内容」的模式。
- **代码块里的图片语法不会被误打包**，行内代码同理。
- 想整站一起走，请用上面的[整站备份](#整站备份推荐)；这个功能只管单篇文章。

## 数据导入导出（JSON，仅数据库记录）

VanBlog 支持数据的导入和导出。点击后台 `站点管理/系统设置/备份恢复`，点击按钮即可导入导出全部站点信息（除了自定义页面和流水线部分）。

导入会恢复文章、草稿、分类、站点信息和图片记录。其中分类会写入分类管理使用的分类表；旧版备份如果只带了分类名（或只在文章上保留了分类名），导入时也会自动补齐分类记录，避免分类管理为空、首页刷新不出文章。导入不会覆盖当前后台登录账号（用户名/密码），避免新机器刚初始化的账户被旧备份顶掉后无法登录；文章上的作者字段仍会随文章一起导入。导入完成后会触发前台增量渲染，稍候刷新首页即可看到文章。

需要注意的是，这种 JSON 导入导出并不会实际导出图床中的图片本身，而是导入导出其图片记录以便检索，也**不含评论**。要连文件一起备份，请用上面的[整站备份](#整站备份推荐)；只想单独拿图片/附件的话，可以用「图片管理 → 导出全部图片」、「附件管理 → 导出全部附件」，或直接备份 `/app/static/` 目录（见 [附件管理](../features/attachment.md)）。

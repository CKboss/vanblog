VanBlog 支持添加自定义权限的协作者用户。

你需要在 `站点管理/系统设置/用户设置` 中进行相关设置:

## 账户权限

::: warning 协作者清单报 404「站点缺少管理员账户」

这说明数据库里**找不到 `id` 为 0 的管理员**（正常站点一定有）。以前这种情况返回 500，
看不出原因；现在返回 404 并直接指路。它通常意味着库被恢复坏了、或者恢复了一份不含用户的归档。

照这个顺序处理：先跑 `./vanblog.sh doctor` 看体检结论；确认是数据问题就用
`./vanblog.sh restore --offline-full <归档>` 从一份**验过**的整站备份恢复
（这条路径在数据库起不来时也能用，见 [备份与恢复](./backup.md#站点已经起不来了怎么恢复)）。

⚠️ 这里**故意不**降级成「只返回协作者、不返回管理员」：清单的第一行**就是**管理员，
少了他会让后台显示「这个站点没有管理员」—— 一个静默的错误答案比一个报错更糟。
:::

协作者账户**默认只有下面这些**（不需要勾选任何权限就有）：

- **查看**：文章与草稿的列表和详情、分类、标签、图片、附件、文章/草稿的**回收站列表**、
  文章的**历史版本**（列表与单条内容）
- **上传**：图片、附件
- **其它**：把文章/草稿**导出为 Markdown**（含图片打包）、按链接搜文章、查图片被哪些文章引用、
  检测图片里的隐写水印

除这些之外**一律拒绝**：没有对应权限的接口会直接报错，后台也不会显示那个入口。
权限判定过程出错时同样是**拒绝**（不会因为一个异常就把后台敞开）。

您可以在创建协作者时额外授予一些权限：

- 创建-文章
- 修改-文章
- 删除-文章
- 发布-草稿
- 创建-草稿
- 修改-草稿
- 删除-草稿
- 删除-图片
- 替换-图片
- 删除-附件
- 所有权限

![权限授予](https://www.mereith.com/static/img/73ef0844436b7eee71d41b4b0c2033d2.clipboard-2022-09-03.png)

除了拥有 `所有权限` 的协作者外，登录后都将看到精简的 UI：

::: warning 「所有权限」不再包含凭据与高危能力

以前代码里的判定是"含 `all` 就放行**全部**后台路由"，等于除账号本身之外的全部能力。
现在有一张**只有管理员本人**（或管理员签发的 API Token）能碰的排除表，勾了「所有权限」也进不去：

| 只有管理员能做 | 为什么单列出来 |
| --- | --- |
| 改管理员口令 | 改了就能把站长锁在外面 |
| 签发 / 吊销 API Token | API Token 签的是 `{sub:0, role:'admin'}`，**等价超管**、不受协作者权限约束、默认 365 天 |
| 下载 / 删除 / 恢复 / 校验整站备份 | 归档里是整个数据库：全部口令的 scrypt 哈希、`settings` 里的 **jwt 密钥**（拿它能直接签管理员令牌，不用破任何密码）、全部文章 |
| 创建或修改流水线 | 流水线是自定义 JS，在 server 进程里跑 ⇒ **容器内的代码执行** |
| 增删改协作者 | 否则可以自己给自己提权 |
| 改系统设置 | 里面包含定制化注入每个页面的 HTML/CSS/**JS**、图床与评论的第三方凭据、登录防爆破开关 |
| 改反向代理与证书 | 能把流量指到别处 |

勾「所有权限」的协作者**仍然可以**：文章、草稿、图片、附件、评论、分类与标签、导航与友链、
自定义页面、主题、统计、导出 Markdown、ISR（手动触发静态页面更新）。

被拒绝时后台会收到 **403**，服务端日志有一条 WARN 写清"哪条路由、需要什么身份、来的是哪个协作者"，
所以排查时不用猜。

⚠️ 换句话说：「所有权限」现在是"内容全权"，不是"站点全权"。要让人能改设置或跑流水线，
只能给他管理员账号本身。

:::

::: warning 升级后请先复核一遍现有协作者的勾选

**协作者权限在本轮之前从来没有生效过** —— 后台表单、接口 DTO、写库、令牌四处用的字段名不一致，
导致无论勾什么，协作者实际只拿到上面那些默认的只读能力。

修好之后的直接后果：**原本"什么都做不了"的协作者，会突然获得你当初勾过的那些权限。**
所以升级完请到 `站点管理 / 系统设置 / 用户设置` 把每个协作者的勾选复核一遍，
把不该给的取消掉（尤其是「所有权限」）。

不需要做数据迁移：旧的错误字段在入库之前就被丢弃了，库里从来没有存过它。

:::

::: tip 协作者不能与管理员同名

两个方向都会被拒绝，并且错误信息会说明原因：

- 新建协作者时用了管理员的用户名 → **403**「用户名「xxx」与管理员账号相同，不可用于协作者」；
- 给**管理员**改名时撞上某个协作者的用户名 → **400**「用户名「xxx」已被一个协作者占用」。

原因是登录按用户名找账号：同名会让"这个用户名该登进哪个账号"取决于数据库返回顺序，
可能把协作者的密码用到管理员账号上，也可能让人自己登不进去。
⚠️ 「忘记密码」的恢复流程也会把表单里的用户名写回管理员账号，所以那条路同样做了重名检查。

:::

::: tip 协作者看不到加密密码

分类的访问密码对协作者是**脱敏**的（`GET /api/admin/category/all?detail=true` 不给密码字段），
文章侧同理：任何接口都只回「有没有设密码」这个布尔，不回密码也不回哈希。
协作者的口令与管理员一样存 **scrypt** 哈希，详见 [安全与加固](./security.md#口令存储scrypt登录时自动迁移)。

:::

### 作者问题

在创建文章或草稿时，默认的作者为当前登录账户昵称（如果是管理员则是站点管理中设置的作者名称）。

此作者也会显示在前端的版权声明中。
